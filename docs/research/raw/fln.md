# flutter_local_notifications for GeoWake's process-death alarm backstop — current version, mandatory manifest receivers, zonedSchedule/exact-alarm/full-screen-intent config, and upgrade breaking changes

## Summary
GeoWake currently resolves flutter_local_notifications to 19.4.2 (pinned `^19.0.0`), while the latest published version is 22.0.1 (published ~mid-June 2026, ~33 days before 2026-07-18). Since v16.0.0 the plugin declares only the bare minimum in its own manifest, so the app MUST declare the three receivers itself — and GeoWake's AndroidManifest.xml already does so correctly and verbatim to the README (ScheduledNotificationReceiver, ScheduledNotificationBootReceiver with the full BOOT_COMPLETED/MY_PACKAGE_REPLACED/QUICKBOOT intent-filter, and ActionBroadcastReceiver), so the `AndroidScheduleMode.alarmClock` process-death backstop at notification_service.dart:924 is wired correctly for the 19.x line. The backstop config is sound: alarmClock mode uses AlarmManager.setAlarmClock (survives Doze), the app holds SCHEDULE_EXACT_ALARM + USE_EXACT_ALARM, USE_FULL_SCREEN_INTENT with requestFullScreenIntentPermission(), and Importance.max. The single biggest risk is NOT a current bug but the upgrade path: v20.0.0 converted zonedSchedule() (and show/initialize/cancel/periodicallyShow) from positional to named parameters, and GeoWake calls zonedSchedule positionally — so bumping to v20/21/22 is a hard compile break requiring code changes. v21.0.0 also raises floors to Flutter 3.38.1 / Dart 3.10.0 / AGP 8.11.1 (GeoWake's Android SDK config already satisfies compileSdk 36, minSdk 24). No action is required to keep the backstop working today; the receivers and permissions are already correct.

## Caveats
- GeoWake is on 19.4.2, which is 3 major versions behind latest (22.0.1). The backstop works correctly today; no action is required to keep it working. But do NOT do a blind bump: v20.0.0 converts zonedSchedule() to named parameters and GeoWake calls it positionally at lib/services/notification_service.dart:924, so >=20 is a guaranteed compile break. A safe upgrade also needs Flutter >=3.38.1 / Dart >=3.10.0 (v21 floor).
- The v20 named-parameter breaking change applies to plugin METHODS (initialize/show/cancel/periodicallyShow/zonedSchedule), not the AndroidNotificationDetails constructor. GeoWake constructs AndroidNotificationDetails('geowake_backstop_channel_v1', 'GeoWake Backstop Alarm', ...) positionally; that constructor is not named in the v20 breaking-change list, so it is very likely still positional in v22 — but confirm against the v22 API docs before migrating rather than assuming.
- USE_EXACT_ALARM (which GeoWake declares alongside SCHEDULE_EXACT_ALARM) is auto-granted but is restricted by Google Play policy to apps whose core function is an alarm clock / calendar / timer. GeoWake is a wake-alarm app so it plausibly qualifies, but this is a Play-review policy risk that is independent of the plugin and should be validated with Play policy, not just the plugin docs. SCHEDULE_EXACT_ALARM alone (revocable by user/OEM on Android 13+) is the safer fallback.
- The backstop's real-world reliability on India-market OEMs (Xiaomi/MIUI, Oppo/ColorOS, Vivo, Realme) is a device-behavior problem, not a plugin-config problem: even with correct receivers + exact-alarm + setAlarmClock, aggressive OEM battery managers can kill AlarmManager delivery unless the user grants autostart/no-battery-optimization. That is why GeoWake's manifest queries the OEM security-center packages — the plugin config here is correct; OEM allow-listing is the remaining risk.
- Version publish date is derived from pub.dev's relative '33 days ago' as of 2026-07-18 (≈mid-June 2026); treat the exact calendar date as approximate.
