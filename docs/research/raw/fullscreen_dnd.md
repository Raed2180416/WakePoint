# Guaranteeing a visible + audible wake on modern Android (Android 13–15 / 2026): full-screen intent, DND bypass, and POST_NOTIFICATIONS for GeoWake (alarm app)

## Summary
On modern Android a wake alarm needs THREE independent grants, none automatic: (1) POST_NOTIFICATIONS runtime permission (API 33+) or you cannot post anything at all; (2) USE_FULL_SCREEN_INTENT, which since Android 14 (API 34) is a special-access, user-revocable permission auto-granted ONLY to apps whose core function is alarms or calling — GeoWake qualifies but must still submit the Play Console full-screen-intent declaration and code a canUseFullScreenIntent()==false fallback via the ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT deep-link; (3) DND bypass, which requires the special-access ACCESS_NOTIFICATION_POLICY grant (deep-link ACTION_NOTIFICATION_POLICY_ACCESS_SETTINGS) BEFORE setBypassDnd(true) on the channel has any effect. The single most important design fact: a full-screen intent only launches the full-screen activity when the device is LOCKED; when unlocked and in use it degrades to a heads-up notification — so the audible ring must come from a foreground service + IMPORTANCE_HIGH channel with an alarm sound / STREAM_ALARM, never from the FSI activity alone. Play enforcement of the FSI declaration has been live since Jan 22, 2025; the declaration itself has been required since May 31, 2024. All strings, versions, and dates below were verified against primary Android/AOSP/Play sources this session (2026-07-18).

## Key facts
- **Since Android 14 (API 34), the default USE_FULL_SCREEN_INTENT permission to send full-screen notifications can be granted only to apps that provide calling and alarm functionalities; the permission is special-access and user-revocable (on/off in Settings). GeoWake, being an alarm app, is in the eligible class.** — `Manifest string: android.permission.USE_FULL_SCREEN_INTENT; eligible = calling + alarm apps only (API 34+)` [high] (as_of fetched 2026-07-18; Android 14 (API 34)) https://developer.android.com/about/versions/14/behavior-changes-14
- **AOSP confirms the platform (not just the Play Store) restricts default FSI grant to calling/alarm apps: the default USE_FULL_SCREEN_INTENT permission can be granted only to apps that provide calling and alarm functionalities. Apps check status with NotificationManager#canUseFullScreenIntent(); users manage it under Special app access > Manage full screen intents.** — `canUseFullScreenIntent() gate; Settings menu 'Manage full screen intents'` [high] (as_of fetched 2026-07-18) https://source.android.com/docs/core/permissions/fsi-limits
- **NotificationManager.canUseFullScreenIntent() was added in API level 34. If it returns false, launch the settings deep-link to let the user grant it. This is the required fallback even for alarm apps, because the user can revoke the permission at any time and non-declared/new installs may default to off.** — `canUseFullScreenIntent() — added API 34; returns boolean` [high] (as_of fetched 2026-07-18; API 34) https://developer.android.com/about/versions/14/behavior-changes-14
- **Deep-link to grant FSI: Intent action constant Settings.ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT, added API 34. The intent's data URI MUST specify the app package (Uri.parse('package:'+packageName)). Microsoft's generated Android bindings confirm ApiSince=34 and the package-URI input requirement.** — `Settings.ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT (string value 'android.settings.MANAGE_APP_USE_FULL_SCREEN_INTENT'), API 34, data = package:<pkg>` [high] (as_of fetched 2026-07-18; API 34) https://learn.microsoft.com/en-us/dotnet/api/android.provider.settings.actionmanageappusefullscreenintent?view=net-android-34.0
- **CRITICAL DESIGN CONSTRAINT: a full-screen intent only launches the full-screen activity when the device is LOCKED (a full-screen activity appears, covering the lockscreen). When the device is UNLOCKED / in active use, it degrades to a heads-up notification (appears in an expanded form with options for handling or dismissing). Therefore GeoWake must NOT rely on the FSI activity to make sound — the audible ring must be driven independently.** — `Locked -> full activity; Unlocked -> heads-up only` [high] (as_of fetched 2026-07-18) https://developer.android.com/develop/ui/views/notifications/build-notification
- **To launch the full-screen activity the app must (a) hold USE_FULL_SCREEN_INTENT in the manifest (required since target Android 10 / API 29) and (b) call NotificationCompat.Builder.setFullScreenIntent(pendingIntent, true) with a high-importance channel / high-priority notification.** — `setFullScreenIntent(pi, true); USE_FULL_SCREEN_INTENT required since API 29 target` [high] (as_of fetched 2026-07-18) https://developer.android.com/develop/ui/views/notifications/build-notification
- **Google Play requires a full-screen-intent declaration in Play Console for any app using USE_FULL_SCREEN_INTENT and targeting Android 14+. Only apps whose core functionality is setting an alarm or receiving phone or video calls are automatically granted the permission; all others must prompt the user and gracefully degrade if denied.** — `Play Console 'App content' full-screen-intent declaration; alarm/calling = core-functionality qualifier` [high] (as_of fetched 2026-07-18) https://support.google.com/googleplay/android-developer/answer/13392821?hl=en
- **Play FSI timeline (changed in last 18 months, FLAG): declaration required starting May 31, 2024; enforcement — Starting January 22, 2025, for apps targeting Android 14+, only apps that have calling or alarm functionalities will have this permission enabled by default. Non-qualifying apps must prompt on new installs.** — `Declaration: 2024-05-31; enforcement/default-by-functionality: 2025-01-22` [high] (as_of fetched 2026-07-18) https://support.google.com/googleplay/android-developer/answer/13392821?hl=en
- **POST_NOTIFICATIONS is a runtime permission on Android 13+ (API 33). Manifest: android.permission.POST_NOTIFICATIONS. On a fresh install on Android 13+, notifications are OFF by default; the app must request the permission and the user must grant it before any notification (including foreground-service notifications) is shown.** — `android.permission.POST_NOTIFICATIONS — runtime, API 33+, default OFF on fresh install` [high] (as_of fetched 2026-07-18; API 33) https://developer.android.com/develop/ui/views/notifications/notification-permission
- **POST_NOTIFICATIONS request flow: with targetSdk 33+ the app fully controls timing — request via registerForActivityResult(ActivityResultContracts.RequestPermission()) launching Manifest.permission.POST_NOTIFICATIONS. If the user picks 'Don't allow', all channels are blocked (except a few exempt roles); swiping the dialog away leaves state unchanged. Media-session notifications and self-managed calling apps (MANAGE_OWN_CALLS + ConnectionService + registerPhoneAccount, using CallStyle) are exempt.** — `RequestPermission() contract; deny -> all channels blocked; media + CallStyle exempt` [high] (as_of fetched 2026-07-18; API 33) https://developer.android.com/develop/ui/views/notifications/notification-permission
- **To bypass Do Not Disturb, the app must first hold DND/notification-policy access. AOSP NotificationChannel.setBypassDnd javadoc: Apps with Do Not Disturb policy access (see NotificationManager#isNotificationPolicyAccessGranted()) can set up their own channels this way, but only if the channel hasn't been updated by the user since its creation. Otherwise this value is only modifiable by the system and the notification ranker. So setBypassDnd(true) silently has no effect without the grant.** — `setBypassDnd(true) needs isNotificationPolicyAccessGranted()==true AND channel not user-modified` [high] (as_of fetched 2026-07-18) https://android.googlesource.com/platform/frameworks/base/+/master/core/java/android/app/NotificationChannel.java
- **The DND policy-access grant is a special-access permission gated behind ACCESS_NOTIFICATION_POLICY (declared in manifest) plus a user grant via a settings screen. Check with NotificationManager.isNotificationPolicyAccessGranted(); if false, deep-link the user to Settings.ACTION_NOTIFICATION_POLICY_ACCESS_SETTINGS. Once granted the app may also call setInterruptionFilter(...) to change the global DND filter.** — `Manifest: android.permission.ACCESS_NOTIFICATION_POLICY; check isNotificationPolicyAccessGranted(); grant deep-link = ACTION_NOTIFICATION_POLICY_ACCESS_SETTINGS` [medium] (as_of fetched 2026-07-18) https://developer.android.com/about/versions/14/behavior-changes-14
- **Exact string values of the DND deep-links, verified from AOSP Settings.java source: ACTION_NOTIFICATION_POLICY_ACCESS_SETTINGS = 'android.settings.NOTIFICATION_POLICY_ACCESS_SETTINGS' (no extras required). The per-app notification settings deep-link ACTION_APP_NOTIFICATION_SETTINGS = 'android.settings.APP_NOTIFICATION_SETTINGS' and requires EXTRA_APP_PACKAGE.** — `ACTION_NOTIFICATION_POLICY_ACCESS_SETTINGS = 'android.settings.NOTIFICATION_POLICY_ACCESS_SETTINGS'; ACTION_APP_NOTIFICATION_SETTINGS = 'android.settings.APP_NOTIFICATION_SETTINGS' (+EXTRA_APP_PACKAGE)` [high] (as_of fetched 2026-07-18) https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/provider/Settings.java

## Caveats
- The exact literal string of ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT ('android.settings.MANAGE_APP_USE_FULL_SCREEN_INTENT') follows the AOSP naming convention and is corroborated by the Microsoft binding (registered name + ApiSince=34 + package-URI input), but the AOSP Settings.java fetch this session was truncated and did not surface that specific line — treat the literal value as very-high-confidence-by-convention rather than byte-verified. In code, reference the Settings.ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT constant rather than hardcoding the string.
- Play's FSI dates come from a Play Console Help page that consolidates multiple announcements (May 31 2024 declaration; Jan 22 2025 enforcement). The Android 14 developer behavior-changes page cites May 31 2024 as the deadline for these policy changes, which predates the Jan 22 2025 enforcement — the two pages describe different milestones of the same rollout, not a contradiction.
- setInterruptionFilter() global DND control and setBypassDnd() are related but distinct: bypassing DND for the alarm channel (the right approach for a wake alarm) needs ACCESS_NOTIFICATION_POLICY + setBypassDnd(true); actively flipping the user's whole phone out of DND via setInterruptionFilter is more intrusive and generally unnecessary. Both require the same policy-access grant.
- OEM skins (Xiaomi/MIUI-HyperOS, Vivo/Funtouch, Oppo/ColorOS, Samsung One UI) add their own autostart/background-restriction and lock-screen-notification gates on top of stock Android. Nothing in this report guarantees a wake on those without the additional OEM autostart / battery-unrestricted grants GeoWake already tracks in oem_autostart_service.dart — a well-known India-market gap.
- Audible-ring path was not the primary ask but is the load-bearing complement: because unlocked-device FSI degrades to heads-up, the sound must come from a running foreground service posting an IMPORTANCE_HIGH channel with an alarm sound set on the channel (STREAM_ALARM usage), so the ring survives even when the full-screen activity is suppressed. Verify GeoWake's alarm channel importance and channel sound, not just the FSI wiring.
