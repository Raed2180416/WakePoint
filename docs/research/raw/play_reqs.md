# Google Play 2026 technical requirements (targetSdk, edge-to-edge, 16 KB pages, versionCode) — grounded for GeoWake

## Summary
As of today (2026-07-18), a new or updated app submitted to Google Play must target at least Android 15 / API 35, but that changes to Android 16 / API 36 on 31 Aug 2026 (about 6 weeks away) for all new apps AND updates — so GeoWake's current targetSdkVersion 35 is a short-lived pass that will be rejected for any upload after the deadline; since compileSdk is already 36, bump targetSdkVersion to 36 now. Targeting API 35 already forces edge-to-edge on Android 15 (status/nav bar color setters are deprecated-and-disabled and content draws behind the system bars); targeting API 36 additionally removes the opt-out entirely (windowOptOutEdgeToEdgeEnforcement is disabled) and turns on predictive-back by default, both of which the map/tracking UI must be tested against. The 16 KB page-size requirement has been mandatory since 1 Nov 2025 for any app targeting API 35+ (which GeoWake does), so it already applies: GeoWake's NDK 28.2.13676358 (r28+) aligns its own and Flutter-engine native libs by default, but every bundled third-party .so (google_mobile_ads, maps, geolocator, etc.) must be verified with zipalign -c -P 16 and the project must build with Android Gradle Plugin 8.5.1+. Finally, build.gradle hardcodes versionCode 1 instead of wiring flutter.versionCode, which guarantees the first Play upload succeeds and every subsequent upload is rejected because a versionCode can never be reused or decreased (max 2,100,000,000).

## Key facts
- **Starting 31 August 2026, new apps AND app updates submitted to Google Play must target Android 16 (API level 36) or higher; submissions targeting lower are rejected in Play Console. GeoWake currently sets targetSdkVersion 35, which passes only until this deadline (~6 weeks out).** — `API 36 (Android 16), deadline 2026-08-31` [high] (as_of 2026-07-18) https://developer.android.com/google/play/requirements/target-sdk
- **The requirement currently in effect (since 31 August 2025) is that new apps and updates target Android 15 (API level 35) or higher. This is why targetSdkVersion 35 is accepted today but will not be after 2026-08-31.** — `API 35 required since 2025-08-31; API 36 from 2026-08-31` [high] (as_of 2026-07-18) https://support.google.com/googleplay/android-developer/answer/11926878?hl=en
- **Platform exceptions to the 31 Aug 2026 target: Wear OS and Android Automotive OS need API 35+; Android TV and Android XR need API 34+. GeoWake is a standard phone app, so the API 36 rule applies to it.** — `WearOS/Automotive=API35, TV/XR=API34` [high] (as_of 2026-07-18) https://developer.android.com/google/play/requirements/target-sdk
- **Existing apps that target API 34 or lower become undiscoverable/uninstallable for new users on devices running a newer Android OS than the app's target; already-installed users keep the app. Developers can request an extension to 1 November 2026 for the target-API requirement.** — `extension deadline 2026-11-01` [high] (as_of 2026-07-18) https://developer.android.com/google/play/requirements/target-sdk
- **Apps targeting Android 15 (API 35) are edge-to-edge by default on Android 15 devices — a breaking UI change: content draws behind the status and navigation bars unless the app applies WindowInsets. This already applies to GeoWake at targetSdk 35.** — `edge-to-edge default at targetSdk 35` [high] (as_of 2026-07-18) https://developer.android.com/about/versions/15/behavior-changes-15
- **At targetSdk 35 these color/inset APIs are deprecated AND disabled: Window.setStatusBarColor(int), Window.setNavigationBarColor(int) (gesture nav), Window.setNavigationBarDividerColor(int), Window.setDecorFitsSystemWindows(boolean), and the R.attr statusBarColor / navigationBarColor / navigationBarDividerColor attributes. Setting them has no effect.** — `setStatusBarColor / setNavigationBarColor / setDecorFitsSystemWindows disabled` [high] (as_of 2026-07-18) https://developer.android.com/about/versions/15/behavior-changes-15
- **For apps targeting Android 16 (API 36), R.attr#windowOptOutEdgeToEdgeEnforcement is deprecated and disabled — there is NO way to opt out of edge-to-edge on an Android 16 device. Bumping GeoWake to targetSdk 36 makes handling insets mandatory in the map/tracking UI.** — `windowOptOutEdgeToEdgeEnforcement disabled at API 36` [high] (as_of 2026-07-18) https://developer.android.com/about/versions/16/behavior-changes-16
- **Apps targeting API 36 get predictive-back system animations enabled by default; onBackPressed() is no longer called and KeyEvent.KEYCODE_BACK is no longer dispatched. Stopgap is android:enableOnBackInvokedCallback="false" in the manifest, but the real fix is the predictive-back navigation APIs (Flutter handles this on recent engines — verify GeoWake's back handling).** — `predictive back on by default at API 36` [high] (as_of 2026-07-18) https://developer.android.com/about/versions/16/behavior-changes-16
- **Since 1 November 2025, every new app and every update submitted to Google Play that targets Android 15+ (API 35+) must support 16 KB memory page sizes on 64-bit devices. GeoWake targets API 35, so this requirement already applies to any upload it makes today.** — `16 KB mandatory since 2025-11-01 for targetSdk 35+` [high] (as_of 2026-07-18) https://developer.android.com/guide/practices/page-sizes
- **Pure Java/Kotlin/Dart code is already 16 KB compatible; the requirement only bites on native .so libraries. A Flutter app is affected because it ships native libs (libflutter.so, libapp.so) plus any plugin native code, so all bundled .so files must be 16 KB-aligned.** — `native .so libs must be 16 KB aligned` [high] (as_of 2026-07-18) https://developer.android.com/guide/practices/page-sizes
- **To comply with 16 KB: build with NDK r28+ (aligns .so by default; NDK r27 and lower need linker flags -Wl,-z,max-page-size=16384 -Wl,-z,common-page-size=16384) and Android Gradle Plugin 8.5.1+ (earlier AGP + bundletool may skip zipalign and fail Play deployment). GeoWake's build.gradle already sets ndkVersion "28.2.13676358" (r28+), so its own and Flutter-engine libs align by default — but the AGP version must be confirmed at 8.5.1+.** — `NDK r28+ (have 28.2.13676358), AGP 8.5.1+` [high] (as_of 2026-07-18) https://developer.android.com/guide/practices/page-sizes
- **Verify alignment of the built artifact with zipalign -c -P 16 -v 4 APK_NAME.apk (must report "Verification successful"), or inspect each .so in Android Studio's APK Analyzer for LOAD segments with align 2**14. Prebuilt third-party libs (e.g. google_mobile_ads / GMA SDK, maps, geolocator) are the real risk — a non-aligned .so from any dependency fails the whole build.** — `zipalign -c -P 16 -v 4 app.apk` [high] (as_of 2026-07-18) https://developer.android.com/guide/practices/page-sizes
- **Google's announcement confirms framework readiness: React Native (0.77+), Flutter, and Unity already ship 16 KB-compatible versions; Play Console's app bundle explorer flags where an app needs updating.** — `Flutter/RN 0.77/Unity 16 KB-ready` [high] (as_of 2026-07-18) https://android-developers.googleblog.com/2025/05/prepare-play-apps-for-devices-with-16kb-page-size.html
- **versionCode is a positive integer; Google Play requires each successive upload to use a strictly greater value and forbids reusing a versionCode already uploaded. The maximum value Google Play accepts is 2,100,000,000.** — `max 2,100,000,000; must strictly increase; no reuse` [high] (as_of 2026-07-18) https://developer.android.com/studio/publish/versioning
- **GeoWake's android/app/build.gradle hardcodes 'versionCode 1' (line 22) instead of wiring flutter.versionCode from the pubspec build number (pubspec version is 1.0.0+1). Consequence: the first Play upload succeeds at versionCode 1, and every later upload is rejected ('Version code 1 has already been used') because the value never changes and cannot be reused or lowered. Fix: read flutter.versionCode (or increment the integer each release).** — `hardcoded versionCode 1 blocks 2nd upload` [high] (as_of 2026-07-18) https://developer.android.com/studio/publish/versioning

## Caveats
- Dates and API levels are the Google-published schedule as of 2026-07-18. The 31 Aug 2026 API-36 cutover has not yet passed, so targetSdkVersion 35 is still accepted for uploads today — but for a not-yet-shipped app it is not worth relying on; compileSdk is already 36, so bumping targetSdkVersion to 36 is a one-line change and future-proofs the launch.
- The 'extension to 1 November 2026' applies to the target-API requirement for developers who need more time; it is not a general waiver and should not be part of a launch plan. Treat 31 Aug 2026 = API 36 as the hard target.
- The 16 KB requirement is triggered by targetSdk (API 35+), which GeoWake already meets, so it is live for GeoWake now regardless of the API-36 bump — not a future concern.
- NDK r28+ aligning 'by default' covers code compiled in this build; it does NOT retroactively fix prebuilt .so files shipped inside third-party AARs/plugins. Those must be individually verified and, if unaligned, updated to a 16 KB-compatible dependency version.
- google_mobile_ads and google_maps_flutter pull in Google Play services / GMA native SDKs whose 16 KB alignment depends on the underlying SDK version resolved at build time — verify against the actual built AAB, not the plugin version alone.

## Open questions
- What Android Gradle Plugin version does the GeoWake project resolve (in android/settings.gradle or android/build.gradle)? It must be 8.5.1+ for reliable 16 KB zipalign — not visible in android/app/build.gradle.
- Which Flutter version is actually installed? A pubspec comment references 'Flutter 3.44.6 / Dart 3.12'; confirm the engine ships 16 KB-aligned libflutter.so and supports predictive back before targeting API 36.
- Does the resolved google_mobile_ads 6.0.0 pull a GMA/Play-services native SDK version that is 16 KB-aligned? Verify by running zipalign -c -P 16 on the release AAB's extracted .so set.
- Does GeoWake's foreground-service location tracking touch any local-network APIs (mDNS/SSDP)? Android 16 introduces a local-network access permission (opt-in in 25Q2, mandatory later) that could affect discovery-style networking; not currently a blocker but worth confirming.
- After bumping to targetSdk 36, does the map/tracking UI correctly inset around the status and navigation bars (edge-to-edge is non-optional at API 36), and is the back gesture handled via predictive-back APIs rather than onBackPressed?
