# Aggressive OEM background-process killing on Indian-market Android phones (Xiaomi/HyperOS, Oppo/Vivo/Realme/ColorOS, Samsung One UI) and what a GeoWake foreground-location wake-alarm must do to survive

## Summary
On the OEM skins that dominate India (Xiaomi HyperOS/MIUI, ColorOS-family = Oppo/Realme/OnePlus, Vivo/iQOO Funtouch/OriginOS), a correctly-built foreground location service plus a Doze whitelist (REQUEST_IGNORE_BATTERY_OPTIMIZATIONS) is NOT sufficient. These OEMs run a second, proprietary "Autostart" + battery-saver layer that is independent of Android's standard battery-optimization whitelist and has no public API or documentation; without the user manually enabling Autostart the service is killed on screen-off, on memory pressure, and permanently after reboot. The single highest-leverage action is getting the user to toggle Autostart ON per-OEM, followed by setting battery to "No restrictions"/"Unrestricted" and locking the app in Recents. You can deep-link users to the exact OEM Autostart screen via known ComponentNames (verbatim strings below), but these are unexported/undocumented and must be wrapped in try/catch with a fallback to standard app-details settings. Samsung One UI is the one bright spot: since One UI 6.0 (announced July 2024, under Google pressure) Samsung commits that foreground services of apps targeting Android 14 work as intended, so on Samsung the fix reduces to "Never sleeping apps" + disabling Adaptive Battery. Separately, targeting Android 14 forces FOREGROUND_SERVICE_LOCATION and Android 15 blocks starting a location FGS from BOOT_COMPLETED — both directly affect a wake-alarm that must re-arm after reboot.

## Key facts
- **On Xiaomi/MIUI/HyperOS the Autostart whitelist is a SEPARATE proprietary system from Android's battery-optimization whitelist; requesting REQUEST_IGNORE_BATTERY_OPTIMIZATIONS does NOT account for MIUI's autostart whitelist, so background processing 'simply does not work right' in default settings and there are 'no APIs and no documentation for those extensions'. Autostart must be enabled manually and separately.** — `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS is insufficient on Xiaomi/Oppo/Vivo/Realme; Autostart is a distinct manual toggle` [high] (as_of 2026-07 (page current)) https://dontkillmyapp.com/xiaomi
- **Xiaomi Autostart deep-link ComponentName (works MIUI 10-14 and HyperOS): package com.miui.securitycenter, class com.miui.permcenter.autostart.AutoStartManagementActivity.** — `com.miui.securitycenter / com.miui.permcenter.autostart.AutoStartManagementActivity` [high] (as_of 2026-07 (master branch)) https://raw.githubusercontent.com/judemanutd/AutoStarter/master/autostarter/src/main/java/com/judemanutd/autostarter/AutoStartPermissionHelper.kt
- **Xiaomi battery 'No restrictions' (PowerKeeper) deep-link ComponentName: package com.miui.powerkeeper, class com.miui.powerkeeper.ui.HiddenAppsConfigActivity, launched with String extras 'package_name' (your applicationId) and 'package_label' (app display name). This is the screen that sets an app to No restrictions / not-hidden from the background killer, distinct from Autostart.** — `com.miui.powerkeeper / com.miui.powerkeeper.ui.HiddenAppsConfigActivity + extras package_name, package_label` [medium] (as_of 2026-07) https://github.com/YangXueQingZZ/KeepLiveSample/blob/master/app/src/main/java/mrkang/keeplivesample/IntentWrapper.java
- **HyperOS / HyperOS 2 user path: Autostart moved into per-app permissions — Settings > Apps > [app] > App permissions > Background autostart (MIUI 14+/HyperOS), and battery via Settings > Apps > [app] > Battery saver > No restrictions. HyperOS 2 surfaces a dedicated 'Background autostart' control. Locked/pinned apps (drag app down in Recents to lock) 'will not be cleared from the background even if you clear recent apps'.** — `Background autostart per-app permission + 'No restrictions' battery + lock in Recents` [high] (as_of 2026-07) https://dontkillmyapp.com/xiaomi
- **Even with Autostart + No restrictions enabled, MIUI/HyperOS is known to reset these toggles after system updates or reboots; there is no permanent programmatic guarantee. Locking the app in Recents is what best survives the aggressive 'clear all' and Ultra battery saver.** — `Toggles can silently reset after OTA/reboot; no dev-side permanent fix` [high] (as_of 2026-07) https://dontkillmyapp.com/xiaomi
- **Oppo/ColorOS Autostart deep-link ComponentNames (also used by Realme UI and legacy OnePlus, which share the ColorOS/OPLUS codebase): com.coloros.safecenter/com.coloros.safecenter.startupapp.StartupAppListActivity ; com.coloros.safecenter/com.coloros.safecenter.permission.startup.StartupAppListActivity ; legacy com.oppo.safe/com.oppo.safe.permission.startup.StartupAppListActivity.** — `com.coloros.safecenter/.startupapp.StartupAppListActivity (+ .permission.startup.StartupAppListActivity; legacy com.oppo.safe)` [high] (as_of 2026-07) https://raw.githubusercontent.com/judemanutd/AutoStarter/master/autostarter/src/main/java/com/judemanutd/autostarter/AutoStartPermissionHelper.kt
- **Realme UI user path (no distinct autostart deep-link in AutoStarter; use ColorOS components): Settings > Battery > Power saving settings > App battery management > [app] and enable 'Allow auto-launch', 'Allow background activity', 'Allow foreground activity'; plus disable 'Sleep standby optimization' under Battery. dontkillmyapp states 'No known solution on dev end yet' — user toggles are mandatory.** — `App battery management: Allow auto-launch + Allow background/foreground activity; disable Sleep standby optimization` [high] (as_of 2026-07) https://dontkillmyapp.com/realme
- **Vivo/iQOO (Funtouch OS / OriginOS) Autostart deep-link ComponentNames: com.iqoo.secure/com.iqoo.secure.ui.phoneoptimize.AddWhiteListActivity ; com.vivo.permissionmanager/com.vivo.permissionmanager.activity.BgStartUpManagerActivity ; com.iqoo.secure/com.iqoo.secure.ui.phoneoptimize.BgStartUpManager. User must ALSO set 'High background power consumption' (Settings > Battery > High background power consumption) and 'Unrestricted' battery on Android 13+.** — `com.iqoo.secure/.ui.phoneoptimize.AddWhiteListActivity + com.vivo.permissionmanager/.activity.BgStartUpManagerActivity + 'High background power consumption'` [high] (as_of 2026-07) https://raw.githubusercontent.com/judemanutd/AutoStarter/master/autostarter/src/main/java/com/judemanutd/autostarter/AutoStartPermissionHelper.kt
- **OnePlus (legacy OxygenOS) Autostart deep-link: ComponentName com.oneplus.security/com.oneplus.security.chainlaunch.view.ChainLaunchAppListActivity and/or Intent action com.android.settings.action.BACKGROUND_OPTIMIZE. Newer OnePlus (OxygenOS 12+ merged with ColorOS) uses the com.coloros.safecenter / com.oplus.* components instead; also disable 'Deep optimization/Adaptive Battery' and 'Sleep standby optimization' under Battery > Battery optimization > Advanced optimization.** — `com.oneplus.security/.chainlaunch.view.ChainLaunchAppListActivity or action com.android.settings.action.BACKGROUND_OPTIMIZE; newer = ColorOS components` [medium] (as_of 2026-07) https://dontkillmyapp.com/oneplus
- **Samsung One UI: since One UI 6.0, Samsung guarantees foreground services of apps targeting Android 14 'will be guaranteed to work as intended so long as they are developed according to Android's new foreground service API policy' (announced 07/2024, via collaboration with Google). Practical user fix on Samsung reduces to adding the app to 'Never sleeping apps' (and NOT to 'Sleeping/Deep sleeping apps'), and disabling Adaptive Battery / 'Put unused apps to sleep' in Device Care. Battery deep-link: com.samsung.android.lool/com.samsung.android.sm.battery.ui.BatteryActivity.** — `One UI 6.0 (July 2024): FGS for Android-14-target apps guaranteed; fix = Never sleeping apps + disable Adaptive Battery` [high] (as_of 2024-07 announcement, page current 2026-07) https://dontkillmyapp.com/samsung
- **Standard Android intent actions for the battery-optimization screens (use these as the fallback when OEM deep-links throw): Settings.ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS opens the full list any app can invoke without justification; Settings.ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS shows the direct allow-dialog but is Play-policy-restricted. Check state with PowerManager.isIgnoringBatteryOptimizations(packageName).** — `ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS (list, unrestricted) vs ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS (dialog, restricted)` [high] (as_of 2026-07 (docs current)) https://developer.android.com/training/monitoring-device-state/doze-standby
- **Google Play policy permits ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS only for specific core-function categories: instant-messaging/calling that cannot use FCM, enterprise VOIP, 'Safety apps' (apps that keep users and families safe), and task-automation apps whose core function is scheduling automated actions. A transit wake-alarm plausibly maps to Safety/task-automation, but the low-risk choice is the non-restricted ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS list screen to avoid a policy rejection.** — `Direct-dialog exemption allowed only for messaging/VOIP/safety/task-automation core functions` [medium] (as_of 2026-07) https://developer.android.com/training/monitoring-device-state/doze-standby
- **Targeting Android 14 (API 34): a location foreground service requires the manifest permission android.permission.FOREGROUND_SERVICE_LOCATION AND at least one granted runtime location permission (ACCESS_FINE_LOCATION or ACCESS_COARSE_LOCATION), with android:foregroundServiceType="location" on the <service>. Missing the FGS permission/type throws at startForeground().** — `FOREGROUND_SERVICE_LOCATION (manifest) + ACCESS_FINE/COARSE_LOCATION (runtime) + foregroundServiceType="location"` [high] (as_of 2026-07 (Android 14/15/16 docs)) https://developer.android.com/develop/background-work/services/fgs/service-types
- **Android 15+ (API 35) directly affects a wake-alarm that re-arms after reboot: apps targeting API 35 CANNOT start a location foreground service from a BOOT_COMPLETED broadcast receiver, and to start a location FGS while in the background at all you need ACCESS_BACKGROUND_LOCATION granted (while-in-use restriction). This interacts with OEM Autostart: even where Autostart lets you launch on boot, Android 15 blocks the location FGS start from BOOT_COMPLETED.** — `API 35: no location FGS from BOOT_COMPLETED; ACCESS_BACKGROUND_LOCATION required to start FGS from background` [high] (as_of 2026-07) https://developer.android.com/develop/background-work/services/fgs/service-types
- **dontkillmyapp ranks the worst offenders for background killing led by the OEMs that dominate India — historically Huawei, Xiaomi, OnePlus, then Samsung (and Oppo/Vivo/Realme in the same aggressive tier); stock Android/Nokia/Motorola are 'good'. This confirms GeoWake's India-first user base is disproportionately on the most hostile skins.** — `Worst-tier: Huawei, Xiaomi, OnePlus, Samsung, Oppo/Vivo/Realme (all high-share in India)` [medium] (as_of 2026-07) https://dontkillmyapp.com/

## Caveats
- OEM Autostart/battery ComponentNames are undocumented and unexported. Launching them by explicit ComponentName can throw SecurityException/ActivityNotFoundException (varies by MIUI/ColorOS/Funtouch build and Android 11+ package-visibility rules). Production pattern: try the OEM ComponentName in try/catch, fall back to the next known variant, then fall back to Settings.ACTION_APPLICATION_DETAILS_SETTINGS (android:data package:<id>) or ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS. Never assume a deep-link succeeded — you cannot programmatically read OEM autostart state on most builds (the XomaDev/MIUI-autostart reflection hack is the only partial exception, MIUI-only).
- There is no reliable programmatic way to detect whether the user actually enabled Autostart or 'No restrictions' on Xiaomi/Oppo/Vivo/Realme. Design the onboarding as an explicit guided checklist with a 'I did this' confirmation and a health-check that infers failure (e.g., service was killed while an alarm was armed), rather than trusting a permission API.
- Newer com.oplus.* battery/power ComponentNames for ColorOS 13/14/15 and OxygenOS 13/14/15 were NOT captured verbatim this session; the legacy com.coloros.safecenter autostart components in AutoStarter still resolve on many ColorOS 13/14 builds but coverage on ColorOS 15/OxygenOS 15 is unverified. Validate on a real ColorOS 15 / HyperOS 2 device before shipping the deep-links.
- MIUI/HyperOS is documented to silently reset Autostart and 'No restrictions' after OTA updates or reboots. Any 'set it once' onboarding will decay; plan periodic re-checks / re-prompts. Rooting or custom ROM is the only fully reliable control, which is not a shippable requirement.
- The Xiaomi PowerKeeper (com.miui.powerkeeper.ui.HiddenAppsConfigActivity) deep-link and its extras (package_name/package_label) are sourced from multiple third-party keep-alive libraries rather than Xiaomi documentation (none exists); treat as widely-used-but-unofficial and test per build.
- Samsung's One UI 6.0 FGS guarantee is conditional on the app targeting Android 14 and following the new FGS API policy exactly, and dontkillmyapp notes Samsung has historically re-added optimizations after firmware updates — so verify on current One UI 7 rather than assuming the 2024 commitment holds unchanged.
