# Android foreground services (API 34/35/36) for a continuous location wake-alarm + alarm-sound playback

## Summary
For a transit wake-alarm, continuous background positioning must run under the `location` foregroundServiceType (manifest FOREGROUND_SERVICE + FOREGROUND_SERVICE_LOCATION, runtime ACCESS_FINE/COARSE_LOCATION, plus ACCESS_BACKGROUND_LOCATION to start/run when backgrounded). Critically, `location` and `mediaPlayback` are NOT subject to any runtime cap — only `dataSync`, `mediaProcessing` (6h per 24h, targeting API 35+) and `shortService` (~3 min) are time-limited, so do NOT model long tracking as dataSync. The alarm sound uses `mediaPlayback` (FOREGROUND_SERVICE_MEDIA_PLAYBACK), also uncapped. A single service CAN declare `location|mediaPlayback`, but you must hold the permission for every type you pass to startForeground() or you get a SecurityException; because `location` is a "while-in-use" type, the combined service cannot be started from the background without ACCESS_BACKGROUND_LOCATION. Starting any FGS from the background throws android.app.ForegroundServiceStartNotAllowedException unless one of the documented exemptions applies (exact-alarm completion, high-priority FCM, user notification/widget interaction, battery-optimizations-off, geofence/activity-recognition transition, etc.). Android 14 added mandatory type+permission declaration and the while-in-use SecurityException; Android 15 added the 6h dataSync/mediaProcessing cap and blocked several types (incl. mediaPlayback, dataSync) from BOOT_COMPLETED; Android 16 (API 36) adds no new FGS timeouts but makes jobs running concurrently with an FGS obey JobScheduler runtime quotas.

## Key facts
- **For continuous background positioning use foregroundServiceType="location". Manifest requires FOREGROUND_SERVICE and FOREGROUND_SERVICE_LOCATION; runtime requires ACCESS_FINE_LOCATION or ACCESS_COARSE_LOCATION; and you cannot create a location FGS while the app is in the background unless ACCESS_BACKGROUND_LOCATION is granted.** — `foregroundServiceType="location"; perms FOREGROUND_SERVICE_LOCATION + ACCESS_FINE/COARSE_LOCATION + ACCESS_BACKGROUND_LOCATION` [high] (as_of 2026-07-18 (API 34/35/36)) https://developer.android.com/develop/background-work/services/fgs/service-types
- **The `location` foreground service type has NO runtime time limit. Only dataSync, mediaProcessing and shortService are time-limited. This is the key reason a multi-hour wake-alarm must use `location`, not `dataSync`.** — `location = uncapped; dataSync/mediaProcessing = 6h/24h; shortService = ~3 min` [high] (as_of 2026-07-18 (Android 15+)) https://developer.android.com/develop/background-work/services/fgs/timeout
- **The 6-hour cap applies ONLY to dataSync and mediaProcessing, counted per type over a rolling 24-hour period, and is shared across all of the app's services of that type. It applies to apps targeting Android 15 (API 35) or higher. The timer resets when the user brings the app to the foreground.** — `6 hours per 24-hour window, per type, targetSdk >= 35` [high] (as_of 2026-07-18 (API 35)) https://developer.android.com/about/versions/15/behavior-changes-15
- **At the 6h cap the system calls Service.onTimeout(int,int); the service has a few seconds to call stopSelf(). If it does not, the system throws a fatal android.app.RemoteServiceException ("A foreground service of type dataSync did not stop within its timeout"). Attempting to START a new capped-type FGS after exhaustion throws ForegroundServiceStartNotAllowedException ("Time limit already exhausted for foreground service type dataSync").** — `onTimeout() -> stopSelf(); else RemoteServiceException; restart -> ForegroundServiceStartNotAllowedException` [high] (as_of 2026-07-18 (API 35)) https://developer.android.com/about/versions/15/behavior-changes-15
- **The alarm/wake sound should run under foregroundServiceType="mediaPlayback" with manifest permission FOREGROUND_SERVICE_MEDIA_PLAYBACK. It has no runtime timeout. (Its policy intent is audio/video playback continuation from the background.)** — `foregroundServiceType="mediaPlayback"; FOREGROUND_SERVICE_MEDIA_PLAYBACK; uncapped` [high] (as_of 2026-07-18 (API 34+)) https://developer.android.com/develop/background-work/services/fgs/service-types
- **A single service CAN declare multiple types with the pipe syntax, e.g. android:foregroundServiceType="location|mediaPlayback". At runtime you pass the bitwise-OR of types to startForeground() and only need to pass the types currently in use (e.g. start with FOREGROUND_SERVICE_TYPE_LOCATION, later call startForeground() again with LOCATION|MEDIA_PLAYBACK). The app must hold the permission for every type it passes.** — `android:foregroundServiceType="location|mediaPlayback"; runtime FOREGROUND_SERVICE_TYPE_LOCATION | FOREGROUND_SERVICE_TYPE_MEDIA_PLAYBACK` [high] (as_of 2026-07-18 (API 34+)) https://developer.android.com/develop/background-work/services/fgs/launch
- **If the app is missing any permission for a type passed to startForeground(), the system throws SecurityException. Because `location` is a while-in-use type, a service that includes location cannot be promoted from the background unless the app holds ACCESS_BACKGROUND_LOCATION or meets an exemption — combining it with mediaPlayback does NOT relax that. Practical pattern: promote with only the mediaPlayback bit when firing the alarm from the background to avoid the location while-in-use check.** — `missing type perm -> SecurityException; location while-in-use gate still applies to combined service` [high] (as_of 2026-07-18 (API 34+)) https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start
- **Starting any foreground service while the app is in the background throws android.app.ForegroundServiceStartNotAllowedException on API 31+ unless an exemption applies. (This is distinct from BackgroundServiceStartNotAllowedException, which is for plain background startService() calls; both subclass android.app.ServiceStartNotAllowedException.)** — `android.app.ForegroundServiceStartNotAllowedException (API 31+)` [high] (as_of 2026-07-18 (API 31+)) https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start
- **Background-start exemptions relevant to a wake-alarm include: app currently visible/transitioning from an activity; completing a user action via an exact alarm (AlarmManager); high-priority FCM (RemoteMessage.PRIORITY_HIGH); user tapping a notification/bubble/widget; receiving a geofencing or activity-recognition transition; SYSTEM_ALERT_WINDOW (Android 15+ needs a visible overlay); Companion Device Manager with REQUEST_COMPANION_START_FOREGROUND_SERVICES_FROM_BACKGROUND; and the user disabling battery optimizations for the app.** — `exact-alarm, high-priority FCM, notification/widget tap, geofence transition, battery-opt-off, CDM, SYSTEM_ALERT_WINDOW` [high] (as_of 2026-07-18 (API 31+)) https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start
- **Android 14 (API 34) while-in-use enforcement: if an app in the background creates an FGS of type location, camera, microphone, or (body-sensors) health, the system throws SecurityException because the app does not currently hold the while-in-use permission. Logcat shows: "Foreground service started from background can not have location/camera/microphone access". PermissionChecker.checkSelfPermission() still returns GRANTED, so it does not guard against this.** — `location/camera/microphone/health from background -> SecurityException (targetSdk >= 34)` [high] (as_of 2026-07-18 (API 34)) https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start
- **Android 15 BOOT_COMPLETED restriction: apps targeting API 35+ cannot launch dataSync, camera, mediaPlayback, phoneCall, or mediaProjection foreground services from a BOOT_COMPLETED receiver; microphone has been blocked from BOOT_COMPLETED since Android 14. Attempting it throws ForegroundServiceStartNotAllowedException. This means a wake-alarm cannot silently spin up location's sibling media/alarm-sound FGS at boot — re-arm via AlarmManager/geofence/WorkManager instead. (location itself is not in the BOOT_COMPLETED block list.)** — `BOOT_COMPLETED blocks dataSync/camera/mediaPlayback/phoneCall/mediaProjection (API 35+); microphone since API 34` [high] (as_of 2026-07-18 (API 35)) https://developer.android.com/about/versions/15/changes/foreground-service-types
- **shortService (for finishing critical work) needs NO type-specific permission — only FOREGROUND_SERVICE. It runs ~3 minutes, must implement Service.onTimeout(), cannot be START_STICKY, and cannot start other foreground services; overrunning triggers a failure/ANR referencing FOREGROUND_SERVICE_TYPE_SHORT_SERVICE.** — `shortService: only FOREGROUND_SERVICE perm; ~3 min limit` [high] (as_of 2026-07-18 (API 34+)) https://developer.android.com/develop/background-work/services/fgs/service-types
- **Android 16 (API 36) introduces NO new foreground-service timeout or type restrictions. The one adjacent change: jobs (JobScheduler/WorkManager) that execute concurrently with a foreground service now adhere to job runtime quotas (previously exempt). Test with adb: am compat enable OVERRIDE_QUOTA_ENFORCEMENT_TO_FGS_JOBS <pkg>. The 6h dataSync/mediaProcessing cap and all Android 15 FGS rules carry forward unchanged.** — `No new FGS caps in API 36; concurrent jobs now obey job runtime quotas` [high] (as_of 2026-07-18 (API 36)) https://developer.android.com/about/versions/16/behavior-changes-all
- **You can enable the dataSync/mediaProcessing timeout on a pre-API-35 app for testing on an Android 15 device via: adb shell am compat enable FGS_INTRODUCE_TIME_LIMITS <package-name>. Useful to verify GeoWake's tracking service is NOT accidentally classified/timed as dataSync.** — `adb shell am compat enable FGS_INTRODUCE_TIME_LIMITS <pkg>` [high] (as_of 2026-07-18 (Android 15 device)) https://developer.android.com/develop/background-work/services/fgs/timeout

## Caveats
- Exception-name nuance the prompt raised: for foreground services the thrown class is android.app.ForegroundServiceStartNotAllowedException (API 31+). BackgroundServiceStartNotAllowedException is a sibling for plain background startService() starts; both extend android.app.ServiceStartNotAllowedException. Docs consistently reference ForegroundServiceStartNotAllowedException for the FGS case.
- mediaPlayback and location are UNCAPPED, but they are still governed by Google Play foreground-service-type policy — you must declare each type's use case in Play Console (Policy > App content) and it is reviewed. A wake-alarm justifies location; the alarm-sound-as-mediaPlayback framing should be documented carefully to avoid policy rejection, since Play scrutinizes mediaPlayback for genuine user-initiated media.
- The while-in-use SecurityException for location fires at startForeground() time based on CURRENT foreground/permission state; holding ACCESS_BACKGROUND_LOCATION is the reliable way to keep the location FGS legal when the app is not visible. Design the arm/fire flow so the location FGS is promoted while an activity is visible, or under a documented exemption (exact alarm, geofence transition, high-priority FCM).
- Doze/OEM battery managers (relevant for India devices — Xiaomi/MIUI, Oppo/Realme/ColorOS, Vivo/Funtouch, Samsung) are a separate reliability axis from AOSP FGS rules and are NOT covered by these developer.android.com pages; they can still kill an uncapped location FGS. AlarmManager setAlarmClock/setExactAndAllowWhileIdle + a full-screen high-priority notification is the AOSP-blessed backstop and doubles as the exact-alarm background-start exemption.
- This research treats today as 2026-07-18; Android 16 (API 36) is the current release surface in the task. All facts were fetched live from developer.android.com this session; version-gated behavior is keyed to targetSdk 34/35/36 as noted per fact.
