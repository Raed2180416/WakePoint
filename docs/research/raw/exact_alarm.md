# Exact alarms on modern Android for GeoWake's never-late transit wake-alarm backstop (SCHEDULE_EXACT_ALARM vs USE_EXACT_ALARM, setAlarmClock, Play policy eligibility)

## Summary
For a never-late backstop, setAlarmClock() is the correct API: it is the only alarm method that is fully Doze-exempt with no rate quota, is never time-adjusted by the system, and forces the device out of low-power mode shortly before firing. setExactAndAllowWhileIdle() is only partially Doze-exempt and is capped at once per 9 minutes per app while in Doze, so it is unsuitable as the primary guarantee. On API 31+, setAlarmClock() still requires one of the two "Alarms & reminders" permissions (SecurityException otherwise) — GeoWake uses AndroidScheduleMode.alarmClock via flutter_local_notifications, so a permission is mandatory. The real decision is which permission to declare. GeoWake's manifest currently declares BOTH SCHEDULE_EXACT_ALARM and USE_EXACT_ALARM, and targets API 35; declaring USE_EXACT_ALARM opts the app into Google Play's restricted-permission policy, which limits USE_EXACT_ALARM to apps whose core user-facing function is "an alarm or timer app" or "a calendar app that shows event notifications." A location-triggered transit wake-alarm is a defensible-but-gray fit (it genuinely is a wake alarm, but exact alarms serve only as an ETA backstop, and Google reviews this narrowly and has bounced reminder-style apps). The lower-risk path is to declare ONLY SCHEDULE_EXACT_ALARM (user-granted, denied-by-default on Android 14+, no Play policy declaration), gate every schedule on canScheduleExactAlarms(), deep-link to settings via ACTION_REQUEST_SCHEDULE_EXACT_ALARM when false, and re-arm on the permission-state-changed and BOOT_COMPLETED broadcasts.

## Key facts
- **Two permissions govern exact alarms: SCHEDULE_EXACT_ALARM (android.permission.SCHEDULE_EXACT_ALARM, added API 31/Android 12, user-granted and user-revocable) and USE_EXACT_ALARM (android.permission.USE_EXACT_ALARM, added API 33/Android 13, auto-granted at install and NOT user-revocable). An app declares ONE of them, not both by necessity.** — `SCHEDULE_EXACT_ALARM = API31+, revocable; USE_EXACT_ALARM = API33+, non-revocable` [high] (as_of 2026-07-18) https://developer.android.com/develop/background-work/services/alarms/schedule
- **setAlarmClock() is the only alarm method fully exempt from Doze: 'Alarms set with setAlarmClock() continue to fire normally. The system exits Doze shortly before those alarms fire.' It is never time-adjusted and has NO once-per-9-minutes quota, unlike the AllowWhileIdle methods. This makes it the correct choice for a never-late backstop.** — `setAlarmClock: full Doze exemption, no quota, never deferred/adjusted` [high] (as_of 2026-07-18) https://developer.android.com/training/monitoring-device-state/doze-standby
- **setExactAndAllowWhileIdle() is only PARTIALLY Doze-exempt and is rate-limited: 'Neither setAndAllowWhileIdle() nor setExactAndAllowWhileIdle() can fire alarms more than once per nine minutes, per app.' It is therefore not a substitute for setAlarmClock() when a hard timing guarantee is required.** — `setExactAndAllowWhileIdle: max once / 9 minutes per app in Doze` [high] (as_of 2026-07-18) https://developer.android.com/training/monitoring-device-state/doze-standby
- **On apps targeting Android 12 (API 31) or higher, calling setExact(), setExactAndAllowWhileIdle(), OR setAlarmClock() requires declaring one of the Alarms & reminders permissions or a SecurityException is thrown. setAlarmClock() is NOT exempt from the permission requirement (the only exemption is the setExact() variant that takes an OnAlarmListener, which uses no PendingIntent and does not apply to a process-death backstop). GeoWake's AndroidScheduleMode.alarmClock backstop therefore mandatorily needs a permission.** — `setAlarmClock requires SCHEDULE_EXACT_ALARM or USE_EXACT_ALARM on API 31+` [high] (as_of 2026-07-18) https://developer.android.com/develop/background-work/services/alarms/schedule
- **Google Play restricted-permission policy, verbatim acceptable use for USE_EXACT_ALARM: 'Your app must use the USE_EXACT_ALARM functionality only when your app's core, user facing functionality requires precisely-timed actions, such as: The app is an alarm or timer app. The app is a calendar app that shows event notifications.' It adds: 'If you have a use case for exact alarm functionality that's not covered above, you should evaluate if using SCHEDULE_EXACT_ALARM as an alternative is an option.' Apps that declare USE_EXACT_ALARM without meeting these criteria are disallowed from publishing on Google Play.** — `USE_EXACT_ALARM limited to alarm/timer apps and calendar apps with event notifications` [high] (as_of 2026-07-18) https://support.google.com/googleplay/android-developer/answer/9888170?hl=en
- **A location-based transit wake-alarm like GeoWake is a GRAY-AREA fit for USE_EXACT_ALARM. It has a plausible claim ('the app is an alarm app' — its core user-facing function is to wake the user), but the exact alarm is used only as an ETA/process-death backstop rather than as the primary user-set clock alarm, and Google's official guidance directs non-core/reminder-style cases to SCHEDULE_EXACT_ALARM instead. There is no policy line that explicitly blesses location-triggered alarms, so eligibility is a case-by-case Play review judgment, not a guarantee.** [medium] (as_of 2026-07-18) https://support.google.com/googleplay/android-developer/answer/9888170?hl=en
- **On Android 14 (API 34) and higher, SCHEDULE_EXACT_ALARM is denied by default (no longer pre-granted) for newly installed apps that target Android 13 (API 33)+ . GeoWake targets API 35, so this applies. Exemptions that are auto-allowed: apps signed with the platform certificate, privileged apps, apps on the power/battery-optimization allowlist (REQUEST_IGNORE_BATTERY_OPTIMIZATIONS), and SYSTEM_WELLBEING role holders. If the permission was already granted before an OS upgrade to 14, it is preserved; a backup-and-restore transfer to a new Android 14 device leaves it denied.** — `SCHEDULE_EXACT_ALARM denied-by-default on Android 14+ for API33+ targets` [high] (as_of 2026-07-18) https://developer.android.com/about/versions/14/changes/schedule-exact-alarms
- **Runtime flow when relying on SCHEDULE_EXACT_ALARM: call AlarmManager.canScheduleExactAlarms() before every schedule; if false, either fall back to an inexact method or send the user to the 'Alarms & reminders' system screen via Intent(ACTION_REQUEST_SCHEDULE_EXACT_ALARM) after in-app justification. Register a receiver for ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED — when the permission is revoked the app is stopped and all future exact alarms are cancelled, so on this broadcast (and on BOOT_COMPLETED) you must re-check canScheduleExactAlarms() and reschedule.** — `canScheduleExactAlarms() gate + ACTION_REQUEST_SCHEDULE_EXACT_ALARM + ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED receiver` [high] (as_of 2026-07-18) https://developer.android.com/develop/background-work/services/alarms/schedule
- **With USE_EXACT_ALARM held, canScheduleExactAlarms() always returns true (auto-granted, non-revocable), so no runtime gate or settings deep-link is needed — the trade-off is being subject to the Play restricted-permission review. With only SCHEDULE_EXACT_ALARM, canScheduleExactAlarms() can be false and must be handled. Declaring both does not remove the Play policy obligation: Play enforces the USE_EXACT_ALARM restricted-permission policy on the mere presence of USE_EXACT_ALARM in the manifest, so GeoWake's current manifest (declares both) is fully exposed to that policy while gaining nothing over declaring one.** [medium] (as_of 2026-07-18) https://developer.android.com/develop/background-work/services/alarms/schedule
- **The Google Play Exact Alarm restricted-permission policy has been enforced since its rollout (initial compliance deadline 31 July 2023); it is a restricted permission requiring a Play Console declaration and reviewer approval, and non-compliant apps are blocked from publishing. This predates the 18-month window, but the denied-by-default enforcement on Android 14+ devices (which continues to expand as the Android 14+ install base grows) is the live behavioral change that affects GeoWake today.** — `Policy compliance deadline: 31 July 2023` [medium] (as_of 2026-07-18) https://support.google.com/googleplay/android-developer/answer/9888170?hl=en

## Caveats
- The setAlarmClock() permission question has conflicting third-party sources. The authoritative Android 'Schedule alarms' guide groups setAlarmClock() with the exact-alarm methods that require declaring an Alarms & reminders permission on API 31+ (SecurityException otherwise); treat setAlarmClock() as REQUIRING the permission. The only documented exemption is the setExact() overload taking an OnAlarmListener, which does not apply to a PendingIntent-based process-death backstop.
- Whether GeoWake specifically qualifies for USE_EXACT_ALARM is a Play reviewer judgment, not a settled rule. The policy names 'alarm or timer app' and 'calendar app that shows event notifications'; a location-triggered wake alarm is arguable but not explicitly enumerated. If you declare USE_EXACT_ALARM, be prepared to justify 'core user-facing function is a wake alarm' in the Play Console declaration, and have a SCHEDULE_EXACT_ALARM fallback ready if rejected.
- The exact 31 July 2023 initial compliance date comes from Google's Play policy announcement as surfaced in search; the OMA mirror page (orangeoma.zendesk.com) returned HTTP 403 and could not be fetched this session for verbatim confirmation. The living policy text was confirmed verbatim from support.google.com/.../answer/9888170.
- GeoWake's manifest (android/app/src/main/AndroidManifest.xml lines 19-20) declares BOTH permissions and targets API 35 (build.gradle line 21). Declaring both means the app is on the hook for the USE_EXACT_ALARM restricted policy with no functional benefit over a single declaration; there is also a known Play Console friction where removing USE_EXACT_ALARM from a previously-published app can require a declaration update.

## Open questions
- Decide product positioning: commit to USE_EXACT_ALARM (frictionless auto-grant, no runtime gate, but restricted-permission Play review and rejection risk) OR drop to SCHEDULE_EXACT_ALARM only (no Play declaration, but denied-by-default on Android 14+ requires the canScheduleExactAlarms() gate, settings deep-link, and re-arm receivers). Do not keep both.
- If staying on SCHEDULE_EXACT_ALARM: confirm the app implements the ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED receiver and re-checks canScheduleExactAlarms() there and on BOOT_COMPLETED — otherwise a silent revocation permanently disables the never-late backstop.
- Because canScheduleExactAlarms() can be false on Android 14+ devices, define the degraded-mode behavior (e.g., fall back to setExactAndAllowWhileIdle within its once-per-9-minute Doze quota, or an always-on foreground-service polling path) so 'never late' still holds when exact-alarm permission is denied.
- Verify battery-optimization allowlisting (REQUEST_IGNORE_BATTERY_OPTIMIZATIONS is already declared): apps on the power allowlist are auto-allowed exact alarms, which can serve as a secondary path to guaranteed delivery on Android 14+ even without SCHEDULE_EXACT_ALARM being user-granted.
