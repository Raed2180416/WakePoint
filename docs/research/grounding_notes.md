## 1. Android foreground services (API 34/35/36) — types + runtime timeout
**Verifier verdict: SOLID**

### Executive summary
For a transit wake-alarm, continuous background positioning must run under the `location` foregroundServiceType (manifest `FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_LOCATION`; runtime `ACCESS_FINE/COARSE_LOCATION`; plus `ACCESS_BACKGROUND_LOCATION` to start/run when backgrounded). The central architectural fact: `location` and `mediaPlayback` are **NOT** subject to any runtime cap — only `dataSync`, `mediaProcessing` (6h/24h, targeting API 35+) and `shortService` (~3 min) are time-limited. **Do NOT model long tracking as `dataSync`.** The alarm sound uses `mediaPlayback` (also uncapped). A single service can declare `location|mediaPlayback`, but you must hold the permission for every type passed to `startForeground()` or get a `SecurityException`; because `location` is "while-in-use", the combined service can't be started from the background without `ACCESS_BACKGROUND_LOCATION`. Starting any FGS from the background throws `ForegroundServiceStartNotAllowedException` unless a documented exemption applies. Android 16 (API 36) adds no new FGS timeouts.

### Confirmed key facts
- **Location FGS declaration & permissions** — `foregroundServiceType="location"`; manifest `FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_LOCATION`; runtime `ACCESS_FINE_LOCATION` or `ACCESS_COARSE_LOCATION`; cannot be created while backgrounded unless `ACCESS_BACKGROUND_LOCATION` granted. — https://developer.android.com/develop/background-work/services/fgs/service-types — *as_of 2026-07-18 (API 34/35/36)*
- **`location` type has NO runtime time limit** — `location` = uncapped; `dataSync`/`mediaProcessing` = 6h/24h; `shortService` = ~3 min. This is why a multi-hour wake-alarm must use `location`, not `dataSync`. — https://developer.android.com/develop/background-work/services/fgs/timeout — *as_of 2026-07-18 (Android 15+)*
- **6-hour cap scope** — 6 hours per rolling 24-hour window, **per type**, shared across all the app's services of that type, applies to apps targeting **API 35+**; timer resets when the user brings the app to the foreground. — https://developer.android.com/about/versions/15/behavior-changes-15 — *as_of 2026-07-18 (API 35)*
- **Cap-exhaustion behavior** — at the cap the system calls `Service.onTimeout(int,int)`; the service has a few seconds to `stopSelf()`, else a fatal `android.app.RemoteServiceException` ("A foreground service of type … did not stop within its timeout"). Starting a new capped-type FGS after exhaustion throws `ForegroundServiceStartNotAllowedException` ("Time limit already exhausted…"). — https://developer.android.com/about/versions/15/behavior-changes-15 — *as_of 2026-07-18 (API 35)*
- **Alarm-sound FGS** — `foregroundServiceType="mediaPlayback"` + manifest `FOREGROUND_SERVICE_MEDIA_PLAYBACK`; no runtime timeout. — https://developer.android.com/develop/background-work/services/fgs/service-types — *as_of 2026-07-18 (API 34+)*
- **Combined types** — `android:foregroundServiceType="location|mediaPlayback"`; at runtime pass the bitwise-OR of the types currently in use (e.g. start with `FOREGROUND_SERVICE_TYPE_LOCATION`, later re-call `startForeground()` with `LOCATION|MEDIA_PLAYBACK`). Must hold the permission for every type passed. — https://developer.android.com/develop/background-work/services/fgs/launch — *as_of 2026-07-18 (API 34+)*
- **Missing-permission & while-in-use gate** — missing any type permission → `SecurityException`; because `location` is while-in-use, a combined service that includes `location` still cannot be promoted from the background without `ACCESS_BACKGROUND_LOCATION` (combining with `mediaPlayback` does not relax it). Practical pattern: promote with only the `mediaPlayback` bit when firing from background. — https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start — *as_of 2026-07-18 (API 34+)*
- **Background-start exception class** — `android.app.ForegroundServiceStartNotAllowedException` (API 31+); sibling `BackgroundServiceStartNotAllowedException` covers plain background `startService()`; both extend `android.app.ServiceStartNotAllowedException`. — https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start — *as_of 2026-07-18 (API 31+)*
- **Background-start exemptions** — visible/transitioning activity; exact-alarm completing a user action; high-priority FCM (`PRIORITY_HIGH`); user tapping notification/bubble/widget; geofencing / activity-recognition transition; `SYSTEM_ALERT_WINDOW` (Android 15+ needs a visible overlay); Companion Device Manager (`REQUEST_COMPANION_START_FOREGROUND_SERVICES_FROM_BACKGROUND`); battery-optimizations-off. — https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start — *as_of 2026-07-18 (API 31+)*
- **Android 14 while-in-use enforcement** — creating an FGS of type location/camera/microphone/body-sensors from the background throws `SecurityException`; `PermissionChecker.checkSelfPermission()` still returns GRANTED, so it does NOT guard against this. — https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start — *as_of 2026-07-18 (API 34)*
- **Android 15 BOOT_COMPLETED block** — apps targeting API 35+ cannot launch `dataSync`, `camera`, `mediaPlayback`, `phoneCall`, or `mediaProjection` FGS from a `BOOT_COMPLETED` receiver (`microphone` blocked since API 34); `location` is **not** on the block list. So re-arm the alarm-sound (mediaPlayback) FGS via AlarmManager/geofence/WorkManager, not at boot. — https://developer.android.com/about/versions/15/changes/foreground-service-types — *as_of 2026-07-18 (API 35)*
- **shortService** — needs no type-specific permission (only `FOREGROUND_SERVICE`); ~3 min; must implement `Service.onTimeout()` (see correction below); cannot be START_STICKY; cannot start other FGS. — https://developer.android.com/develop/background-work/services/fgs/service-types — *as_of 2026-07-18 (API 34+)*
- **Android 16 (API 36)** — introduces NO new FGS timeout/type restrictions. Only adjacent change: jobs running concurrently with an FGS now obey JobScheduler runtime quotas. Test: `adb ... am compat enable OVERRIDE_QUOTA_ENFORCEMENT_TO_FGS_JOBS <pkg>`. — https://developer.android.com/about/versions/16/behavior-changes-all — *as_of 2026-07-18 (API 36)*
- **Test flag** — enable the dataSync/mediaProcessing timeout on a pre-API-35 app on an Android 15 device: `adb shell am compat enable FGS_INTRODUCE_TIME_LIMITS <pkg>`. Useful to confirm GeoWake's tracking service is NOT accidentally timed as `dataSync`. — https://developer.android.com/develop/background-work/services/fgs/timeout — *as_of 2026-07-18 (Android 15 device)*

### Disputed / corrections
- **`shortService` "must implement onTimeout()"** — *minor over-statement.* The service-types page describes implementing `onTimeout()` as strongly-recommended best practice, not a hard requirement (and `Service.onTimeout()` does not exist on Android 13 and lower). Overrunning still triggers a failure/ANR, so the risk framing holds. **Correction:** reword to "should (strongly recommended) implement `Service.onTimeout()` and stop within ~3 minutes." — https://developer.android.com/develop/background-work/services/fgs/service-types

### Open questions
- `MissingForegroundServiceTypeException` full reference wording could not be retrieved this session (thrown when a targetSdk-34+ app calls `startForeground()` without a declared `foregroundServiceType`).
- Whether GeoWake's `lib/services/trackingservice.dart` actually declares `foregroundServiceType="location"` (uncapped) vs anything resembling `dataSync` should be verified against `AndroidManifest.xml` — highest-leverage check for never-late reliability.
- Play-review outcome for declaring the alarm-sound as `mediaPlayback` vs `specialUse` is review-dependent; a `specialUse` declaration with written justification is the documented fallback.
- **OEM caveat (not an AOSP defect):** OEM battery managers on India-market devices (Xiaomi/MIUI, Oppo/ColorOS, Vivo/Funtouch, Samsung) can still kill an uncapped `location` FGS. AOSP timeout-exemption ≠ protection from OEM app-kill; pair this analysis with `oem_autostart_service.dart` mitigations. `setAlarmClock`/`setExactAndAllowWhileIdle` + full-screen high-priority notification is the AOSP-blessed backstop.

## 2. Exact alarms + `setAlarmClock()` + Doze
**Verifier verdict: MOSTLY-SOLID**

### Executive summary
For a never-late backstop, `setAlarmClock()` is the correct API: it is the only alarm method fully Doze-exempt with no rate quota, is never time-adjusted, and forces the device out of low-power mode shortly before firing. `setExactAndAllowWhileIdle()` is only partially Doze-exempt and rate-limited, so it is unsuitable as the primary guarantee. On API 31+, `setAlarmClock()` still requires one of the two "Alarms & reminders" permissions (`SecurityException` otherwise). The real decision is **which permission to declare**. GeoWake's manifest currently declares **both** `SCHEDULE_EXACT_ALARM` and `USE_EXACT_ALARM` and targets API 35; declaring `USE_EXACT_ALARM` opts the app into Google Play's restricted-permission policy, which limits it to apps whose core function is "an alarm or timer app" or "a calendar app that shows event notifications." A location-triggered transit wake-alarm is a defensible-but-gray fit. The lower-risk path is to declare **only** `SCHEDULE_EXACT_ALARM`, gate every schedule on `canScheduleExactAlarms()`, deep-link via `ACTION_REQUEST_SCHEDULE_EXACT_ALARM` when false, and re-arm on the permission-state-changed and BOOT_COMPLETED broadcasts.

### Confirmed key facts
- **Two permissions** — `SCHEDULE_EXACT_ALARM` (API 31, user-granted, revocable by user *and* system, not pre-granted to fresh installs targeting API 33+) vs `USE_EXACT_ALARM` (API 33, auto-granted at install, NOT user-revocable). Declare one, not both by necessity. — https://developer.android.com/develop/background-work/services/alarms/schedule — *as_of 2026-07-18*
- **`setAlarmClock()` is fully Doze-exempt** — verbatim: "Alarms set with `setAlarmClock()` continue to fire normally. The system exits Doze shortly before those alarms fire." No 9-minute quota; never time-adjusted → correct choice for a never-late backstop. — https://developer.android.com/training/monitoring-device-state/doze-standby — *as_of 2026-07-18*
- **`setExactAndAllowWhileIdle()` is rate-limited** — verbatim: "Neither `setAndAllowWhileIdle()` nor `setExactAndAllowWhileIdle()` can fire alarms more than once per nine minutes, per app." Not a substitute when a hard timing guarantee is required. — https://developer.android.com/training/monitoring-device-state/doze-standby — *as_of 2026-07-18*
- **Permission required on API 31+ for all three** — `setExact()`, `setExactAndAllowWhileIdle()`, AND `setAlarmClock()` need an Alarms & reminders permission or throw `SecurityException`. Only exemption: the `setExact()` overload taking an `OnAlarmListener` (no PendingIntent) — which does NOT apply to a process-death backstop. GeoWake's `AndroidScheduleMode.alarmClock` therefore mandatorily needs a permission. — https://developer.android.com/develop/background-work/services/alarms/schedule — *as_of 2026-07-18*
- **Play `USE_EXACT_ALARM` policy (verbatim)** — acceptable use is only when core user-facing functionality requires precisely-timed actions, "such as: The app is an alarm or timer app. The app is a calendar app that shows event notifications." Directs other cases to `SCHEDULE_EXACT_ALARM`; non-qualifying apps are disallowed from publishing. — https://support.google.com/googleplay/android-developer/answer/9888170?hl=en — *as_of 2026-07-18*
- **GeoWake fit = GRAY area** — plausible "the app is an alarm app" claim, but the exact alarm is used only as an ETA/process-death backstop, and Google directs non-core/reminder cases to `SCHEDULE_EXACT_ALARM`. No policy line explicitly blesses location-triggered alarms → case-by-case Play-review judgment, not a guarantee. *(confidence: medium)* — https://support.google.com/googleplay/android-developer/answer/9888170?hl=en — *as_of 2026-07-18*
- **`SCHEDULE_EXACT_ALARM` denied-by-default on Android 14+** — for newly installed apps targeting API 33+ (GeoWake targets 35). Auto-allowed exemptions: platform-signed apps, privileged apps, power/battery-optimization-allowlist apps (`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`), `SYSTEM_WELLBEING` role holders. OS upgrade preserves an existing grant; backup-and-restore to a new Android 14 device leaves it denied. — https://developer.android.com/about/versions/14/changes/schedule-exact-alarms — *as_of 2026-07-18*
- **Runtime flow (SCHEDULE_EXACT_ALARM path)** — call `AlarmManager.canScheduleExactAlarms()` before every schedule; if false, fall back or deep-link via `Intent(ACTION_REQUEST_SCHEDULE_EXACT_ALARM)`. Register a receiver for `ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED`; on revocation the app is stopped and future exact alarms cancelled, so on that broadcast (and on `BOOT_COMPLETED`) re-check and reschedule. — https://developer.android.com/develop/background-work/services/alarms/schedule — *as_of 2026-07-18*
- **`USE_EXACT_ALARM` held ⇒ `canScheduleExactAlarms()` always true** (auto-granted, non-revocable) → no runtime gate needed, but subject to Play restricted-permission review. Declaring **both** does not remove the Play obligation: Play enforces the `USE_EXACT_ALARM` policy on mere manifest presence, so GeoWake's current manifest is fully exposed while gaining nothing over declaring one. *(confidence: medium)* — https://developer.android.com/develop/background-work/services/alarms/schedule — *as_of 2026-07-18*

### Disputed / corrections
- **"Policy compliance deadline: 31 July 2023" attributed to answer/9888170** — *citation defect.* The verifier fetched that URL and it contains **no** compliance-deadline date. The 31 July 2023 date is genuine (traces to Google's July 2022 announcement of the upcoming restricted permission) but is **not sourced to the cited page** — only to secondary sources (Google's 2022 announcement, the orangeoma.zendesk.com mirror, third-party blogs). **Correction:** keep the date only as historical context, not as sourced to answer/9888170. For the production decision it is immaterial — the live, verifiable constraint is Android 14+ denied-by-default, not the 2023 publishing deadline. — https://support.google.com/googleplay/android-developer/answer/9888170?hl=en
- **"never time-adjusted / no quota" attributed to the Doze page** — *minor sourcing imprecision.* The Doze page supports the Doze-exemption + exit-before-firing part; the "never adjusts delivery time" language lives in the `AlarmManager` reference. Substance correct; cite both pages. — https://developer.android.com/reference/android/app/AlarmManager
- **"denied by default" wording** — the Android 14 doc says "no longer being pre-granted to **most** newly installed apps targeting Android 13 and higher." The word "most" is covered by the enumerated exemptions; "denied by default" is accurate for GeoWake specifically (not platform-signed / privileged / SYSTEM_WELLBEING).

### Open questions
- **Decide product positioning — do not keep both.** Commit to `USE_EXACT_ALARM` (frictionless auto-grant, no runtime gate, but restricted-permission Play review + rejection risk) OR drop to `SCHEDULE_EXACT_ALARM` only (no Play declaration, but denied-by-default on Android 14+ → needs the `canScheduleExactAlarms()` gate, settings deep-link, re-arm receivers).
- If staying on `SCHEDULE_EXACT_ALARM`: confirm the app implements the `ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED` receiver and re-checks on it + on `BOOT_COMPLETED`; otherwise a silent revocation permanently disables the never-late backstop. *(Memory index flags a prior dead-backstop-receiver bug — still an open code-audit item.)*
- Define degraded-mode behavior when exact-alarm permission is denied (fall back to `setExactAndAllowWhileIdle` within its Doze quota, or an always-on FGS polling path) so "never late" still holds.
- Verify battery-optimization allowlisting (`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` already declared): allowlisted apps are auto-allowed exact alarms — a secondary guaranteed-delivery path on Android 14+.

## 3. Full-screen intent + DND bypass + `POST_NOTIFICATIONS`
**Verifier verdict: MOSTLY-SOLID**

### Executive summary
A wake alarm on modern Android needs **three independent grants**, none automatic: (1) `POST_NOTIFICATIONS` runtime permission (API 33+) or you cannot post anything; (2) `USE_FULL_SCREEN_INTENT`, which since Android 14 is a special-access, user-revocable permission auto-granted **only** to apps whose core function is alarms or calling — GeoWake qualifies but must still submit the Play Console FSI declaration and code a `canUseFullScreenIntent()==false` fallback via the `ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT` deep-link; (3) DND bypass, which requires the special-access `ACCESS_NOTIFICATION_POLICY` grant (deep-link `ACTION_NOTIFICATION_POLICY_ACCESS_SETTINGS`) **before** `setBypassDnd(true)` on the channel has any effect. **Load-bearing design fact:** a full-screen intent only launches the full-screen activity when the device is **LOCKED**; when unlocked it degrades to a heads-up notification — so the audible ring must come from a foreground service + `IMPORTANCE_HIGH` channel with an alarm sound / `STREAM_ALARM`, never from the FSI activity alone. Play FSI enforcement has been live since Jan 22, 2025; the declaration required since May 31, 2024.

### Confirmed key facts
- **FSI default grant restricted to calling/alarm apps (API 34+)** — `android.permission.USE_FULL_SCREEN_INTENT`; special-access, user-revocable. GeoWake (alarm) is in the eligible class. — https://developer.android.com/about/versions/14/behavior-changes-14 — *as_of 2026-07-18 (API 34)*
- **Platform-level (not just Play) restriction** — AOSP: the default `USE_FULL_SCREEN_INTENT` can be granted only to apps that provide calling and alarm functionalities; check `NotificationManager#canUseFullScreenIntent()`; user manages it under Settings > Special app access > Manage full screen intents. — https://source.android.com/docs/core/permissions/fsi-limits — *as_of 2026-07-18*
- **`canUseFullScreenIntent()` added API 34** — if false, deep-link to settings; required fallback even for alarm apps (revocable anytime; new installs may default off). — https://developer.android.com/about/versions/14/behavior-changes-14 — *as_of 2026-07-18 (API 34)*
- **FSI grant deep-link** — `Settings.ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT` (API 34); data URI must specify the package (`Uri.parse("package:"+packageName)`). — https://learn.microsoft.com/en-us/dotnet/api/android.provider.settings.actionmanageappusefullscreenintent?view=net-android-34.0 — *as_of 2026-07-18 (API 34)*
- **CRITICAL: locked → full activity; unlocked → heads-up only** — verbatim on the notification-build page. GeoWake must NOT rely on the FSI activity to make sound; drive the ring independently. — https://developer.android.com/develop/ui/views/notifications/build-notification — *as_of 2026-07-18*
- **Launching the FSI activity** — hold `USE_FULL_SCREEN_INTENT` in the manifest (required since target API 29) and call `NotificationCompat.Builder.setFullScreenIntent(pi, true)` with a high-importance channel. — https://developer.android.com/develop/ui/views/notifications/build-notification — *as_of 2026-07-18*
- **Play FSI declaration** — required in Play Console for any app using `USE_FULL_SCREEN_INTENT` targeting Android 14+; only alarm/calling core-functionality apps are auto-granted; all others must prompt + gracefully degrade. — https://support.google.com/googleplay/android-developer/answer/13392821?hl=en — *as_of 2026-07-18*
- **Play FSI timeline (changed <18 months, FLAG)** — declaration required starting **May 31, 2024**; enforcement: "Starting January 22, 2025, for apps targeting Android 14+, only apps that have calling or alarm functionalities will have this permission enabled by default." — https://support.google.com/googleplay/android-developer/answer/13392821?hl=en — *as_of 2026-07-18*
- **`POST_NOTIFICATIONS`** — runtime permission on Android 13+ (`android.permission.POST_NOTIFICATIONS`); notifications OFF by default on fresh install; must be granted before any notification (incl. FGS notifications) shows. — https://developer.android.com/develop/ui/views/notifications/notification-permission — *as_of 2026-07-18 (API 33)*
- **`POST_NOTIFICATIONS` request flow** — with targetSdk 33+ the app controls timing via `registerForActivityResult(ActivityResultContracts.RequestPermission())`. "Don't allow" blocks all channels; swiping away leaves state unchanged. Exempt: media-session notifications and self-managed calling apps (`MANAGE_OWN_CALLS` + `ConnectionService` + `registerPhoneAccount`, `CallStyle`). — https://developer.android.com/develop/ui/views/notifications/notification-permission — *as_of 2026-07-18 (API 33)*
- **`setBypassDnd(true)` needs policy access** — AOSP `NotificationChannel.setBypassDnd` javadoc: works only if `NotificationManager#isNotificationPolicyAccessGranted()` is true AND the channel hasn't been user-modified since creation; otherwise the value is system-/ranker-only. So it silently no-ops without the grant. — https://android.googlesource.com/platform/frameworks/base/+/master/core/java/android/app/NotificationChannel.java — *as_of 2026-07-18*
- **DND policy-access grant** — special-access `ACCESS_NOTIFICATION_POLICY`; check `isNotificationPolicyAccessGranted()`; deep-link `Settings.ACTION_NOTIFICATION_POLICY_ACCESS_SETTINGS`. Once granted, may also call `setInterruptionFilter(...)`. *(confidence: medium — see correction)* — https://developer.android.com/reference/android/app/NotificationManager#isNotificationPolicyAccessGranted() — *as_of 2026-07-18*
- **DND deep-link string values (convention-confidence)** — `ACTION_NOTIFICATION_POLICY_ACCESS_SETTINGS = "android.settings.NOTIFICATION_POLICY_ACCESS_SETTINGS"`; `ACTION_APP_NOTIFICATION_SETTINGS = "android.settings.APP_NOTIFICATION_SETTINGS"` (+`EXTRA_APP_PACKAGE`). — https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/provider/Settings.java — *as_of 2026-07-18*

### Disputed / corrections
- **DND mechanism attributed to the "Android 14 behavior changes" page** — *sourcing mismatch.* Substance is correct and standard, but `ACCESS_NOTIFICATION_POLICY` / `isNotificationPolicyAccessGranted()` / `ACTION_NOTIFICATION_POLICY_ACCESS_SETTINGS` are NOT documented on behavior-changes-14 (which covers FSI, not DND policy access). **Correction:** cite the `NotificationManager` / `Settings` API reference and the `setBypassDnd` javadoc instead. — https://developer.android.com/reference/android/app/NotificationManager#isNotificationPolicyAccessGranted()

The constant **names**, API levels (FSI=34), and package-URI requirement ARE confirmed; the underlying **string values** were not primary-verified (reference constant-value tables didn't render; the Microsoft binding shows the register-name, not the string). **Correction:** in code reference the `Settings.*` constants rather than hardcoding the strings. — https://learn.microsoft.com/en-us/dotnet/api/android.provider.settings.actionmanageappusefullscreenintent?view=net-android-35.0

## 4. Boot resume + Doze/App-Standby + background location (Android 14/15/16)
**Verifier verdict: SOLID**

### Executive summary
You **can** start a `location` FGS from a `BOOT_COMPLETED` receiver — `location` is NOT on the list banned from BOOT_COMPLETED. The real blocker is the while-in-use rule: because BOOT_COMPLETED runs in a background context, a `location` FGS started there throws `ForegroundServiceStartNotAllowedException` **unless `ACCESS_BACKGROUND_LOCATION` is already granted**. So GeoWake's reboot-restart path is only viable with "Allow all the time" background location (settings-only on Android 11+, requested separately after foreground, gated by a Play Permissions Declaration review). For never-miss timing under Doze, the durable primitive is `AlarmManager.setAlarmClock()` — not `setExactAndAllowWhileIdle` (Doze-capped) and not plain jobs/alarms (deferred to maintenance windows). A battery-optimization exemption grants network + partial wakelocks in Doze but does NOT exempt deferred jobs, and Play's Device-and-Network-Abuse policy prohibits requesting it unless core function is adversely affected. Android 16 tightens JobScheduler by enforcing standby-bucket quotas even for jobs running alongside an FGS.

### Confirmed key facts
- **BOOT_COMPLETED is an FGS background-start exemption** — allowed: `ACTION_BOOT_COMPLETED`, `ACTION_LOCKED_BOOT_COMPLETED`, `ACTION_MY_PACKAGE_REPLACED` (subject to per-type restrictions). — https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start — *as_of 2026-07-18 (Android 12–16)*
- **BOOT_COMPLETED FGS-type ban (A15)** — banned: `dataSync`, `camera`, `mediaPlayback`, `mediaProjection`, `phoneCall` (A14+ adds `microphone`); throws `ForegroundServiceStartNotAllowedException`. `location` is NOT banned. Test flag: `FGS_BOOT_COMPLETED_RESTRICTIONS`. — https://developer.android.com/about/versions/15/behavior-changes-15 — *as_of 2026-07-18 (API 35)*
- **Types STILL allowed from BOOT_COMPLETED (A15)** — `location`, `connectedDevice`, `health`, `remoteMessaging`, `specialUse`, `systemExempted`, `shortService`. — https://developer.android.com/about/versions/15/behavior-changes-15 — *as_of 2026-07-18 (API 35)*
