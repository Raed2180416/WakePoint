# 10 — Metro Data & Stop Matching (N-stops correctness)

**Role in the core promise:** GeoWake's core promise is to wake a transit rider *before their stop* — never late, never at the wrong place. When the rider is riding a metro underground where GPS is dead, the app cannot see "you are now 200m from the platform." Instead it must count stops: "you have 3 stops to go, 2, 1, wake up." This subsystem is the ground truth for that count. It answers two questions for every metro leg of a journey: *(1) how many intermediate stops are on this leg, and (2) exactly where along the route (in meters) does each one sit* so the alarm engine can fire "N stops before arrival" at the right physical location. Get the count wrong and you fire at the wrong stop; get the positions wrong and you fire at the right count but the wrong place. Everything here is graded on: **is it better to fire early than late?** — yes, always. The code is riddled with fallbacks that deliberately choose the earlier/safer interpretation whenever the data is uncertain.

## How it works, step by step

There are **two independent data paths**. Only the first one matters for the "never wake late" promise.

### Path A — Live stop-counting (the one that matters)

Consumed by `RouteSessionManager.*` (`lib/services/route_session_manager.dart:435,459,465,538`), `homescreen.dart`, `reroute_constraints.dart`, `maptracking.dart`.

**Step A1 — Parse Directions into raw legs.**
`TransferUtils.extractTransitLegStops(directions)` (`transfer_utils.dart:913`) flattens all steps across all legs into one list, then walks them:
- It tracks cumulative meters in the **polyline domain** (decoding each step's polyline with `decodePolyline`, measuring with `polylineLength`) — *not* the API `distance.value` — because the live progress signal snaps to the stitched polyline, so both must live in the same meter domain (`transfer_utils.dart:947-955`). If a step polyline is empty (test placeholders), it falls back to `distance.value`.
- Between non-stitched steps it adds the geometric gap if `>5 m` (`:959-968`) so leg boundaries line up with the stitched active polyline.
- For a `TRANSIT` step it reads `transit_details.num_stops` (Google's count of *intermediate* stops, excluding boarding + alighting), the line short_name/name, and builds:
  - `stopPositions` via `estimateStopPositions(polyline, numStops)` — uniform placement at fractions `j/(n+1)` for `j=1..n` (`polyline_decoder.dart:109`).
  - `stopMeters` at `legStartMeters + (j/(n+1))·legLength` (`transfer_utils.dart:992-1000`).
  - `isMetro` from `_isMetroTransitStep` (accepts `SUBWAY, HEAVY_RAIL, RAIL, METRO_RAIL, MONORAIL, TRAM, COMMUTER_TRAIN`; `:279-285`).
- Walk/drive steps become zero-stop legs; consecutive same-name non-transit legs are **coalesced** (`:1071-1105`) so a fragmented "walk-walk-walk to station" collapses into one leg with a stable id.

Output: `List<TransitLegStops>` with **uniform, evenly-spaced estimates** and API stop counts. This is the *floor* — always available, even offline, even with no station data.

**Step A2 — Enhance with real station positions (metro mode only).**
`TransferUtils.enhanceTransitLegStopsWithOsm(legs, directions)` (`transfer_utils.dart:1281`). For each metro leg:

1. **Load candidates.** All `allIndiaStops` that pass `_isActiveStop` become `Stop` objects carrying `line` and `city` labels (`:1301-1314`). `_isActiveStop` treats missing status as active, rejects `upcoming/under construction/planned/proposed/approved` (`:250-263`).
2. **Extract the leg's metro polyline.** `_extractTransitPolylines` collects one decoded polyline per metro step in order (`:1700`); `transitPolylineIndex` walks them 1:1 with metro legs.
3. **Radius match.** `StopMatcher.matchStopsToPolyline(polyline, loadedStops, radiusMeters:500, dedupeMeters:80)` → every active station in India within 500 m of *this* polyline, snapped and arc-length ordered (`:1349`). This is nationwide, so it can include parallel/other-line stations.
4. **Canonicalize the leg's identity.**
   - `legLineKey = _canonLine(leg.lineName)` (`:1250`): lowercases, strips HTML entities (`&#x25D9;`), strips punctuation, drops generic words (`line/metro/rail/subway/express/corridor/rapid/transit/route`), then prefers a **color token** (`blue/green/red/yellow/purple/pink/orange/aqua/magenta/violet/…`) as the anchor, else joins remaining alphanumerics (`"Line 7" → "7"`).
   - `legCityKey` = **majority vote** of the matched stops' cities (`:1386-1399`) — the leg has no explicit city, so it's inferred from where its stops physically are.
5. **LINE-FIRST (ordered sequence) — the gold path.** If `kMetroLineSequences[legCityKey][legLineKey]` exists with ≥2 stops (`:1408`), match *that hardcoded ordered sequence* against the polyline. The 500 m radius naturally slices it to just this leg's segment, and because the sequence is pre-ordered and matched by arc length, the count and order are exact and use **only this line's own stations** (`:1409-1436`). `orderedMatches` wins over everything below.
6. **LINE-FILTER — the fallback path.** If no confident sequence matched, keep only `matchedAll` stops whose `_canonLine(stop.line) == legLineKey` and (if both carry a city) same city (`:1438-1450`). This fixes the "WRONG-METRO-STATION-SNAP" bug where a parallel line's station ~140 m away (e.g. Mumbai DN Nagar/Blue vs Andheri West/Yellow) leaked into the wrong leg.
7. **Safety nets (choose the API-uniform leg rather than a wrong OSM leg):**
   - `orderedMatches != null` → use it.
   - `lineFiltered.isEmpty` → **keep the original API-uniform leg** (`:1461-1475`). Never scoop the unfiltered nationwide corridor, because an unknown/dirty line label would inject cross-line stations at wrong positions. On-route-by-construction beats count-accuracy.
   - `lineFiltered` far fewer than API `num_stops` (`< 50%`) **and** the unfiltered set's count is closer → still **keep the API-uniform leg** (`:1476-1497`). The divergence gate only checks *count*, not on-lineness, so preferring the closer-count unfiltered set would substitute phantom off-line stations. Refuse.
   - else use `lineFiltered`.
8. **Dedupe + order.** Collapse by stop `id` (keep the one closest to the polyline), sort by `metersAlongPolyline` (`:1516-1532`).
9. **Endpoint + next-leg filtering.** Drop stops within 50 m of polyline start/end (those are the boarding/alighting stations, not intermediate) (`:1571-1600`). **Mumbai fix:** if a later metro leg exists (scanning *past* intervening walk legs, `:1560-1569`), drop stops that sit within 300 m of the next metro leg's start — they belong to the next line, not this one.
10. **Convert to absolute meters.** Each surviving stop's `metersAlongPolyline` is turned into leg-relative then absolute meters via `progress · legLength` (`:1613-1623`).
11. **G16 divergence gate (the never-late guard).** `osmStopCountDiverges(apiNumStops, osmNumStops)` (`:1197`): if API ≤ 0 → not diverged; if OSM found 0 → **diverged**; else diverged when `|osm−api| > max(1, round(0.2·api))`.
    - **Diverged →** discard the OSM positions, **keep the API-uniform leg** but tag it `stopCountConfidence: 0.5` (`:1650-1660`). Downstream alarm logic treats low-confidence legs as "prefer firing early." A smaller/inconsistent OSM count is *never* adopted blindly, because under-counting = firing late = product death.
    - **Agreed →** adopt the OSM leg: real `stopPositions`/`stopMeters`/`stopNames`, `isActualPositions: true`, `stopCountConfidence: 1.0` (`:1661-1676`).

Output: the enhanced `List<TransitLegStops>`. `RouteSessionManager` then applies a `legScale` correction only if leg meters disagree with the overview polyline length by >10 m (`route_session_manager.dart:482-506`), and persists via `TrackingStateStore.saveTransitLegStops`.

**Step A3 — Runtime counting.** During tracking, `stopsPassed(currentMeters)` counts how many `stopMeters` are ≤ progress (short-circuits because they're sorted; `transfer_utils.dart:169-179`); `stopsRemaining = numStops − stopsPassed`. `countStopsPassed`/`countStopsRemaining` (`:1117-1149`) aggregate across legs. This is what the alarm engine reads to say "2 stops to go."

**Step A4 — Route events.** `buildRouteEvents(directions)` (`:396`) produces `RouteEventBoundary`s for `preBoarding` ("Board Blue Line"), `mode_change` ("Start walking"), and `transfer` (at an interchange). It distinguishes a genuine "Start walking" from an *interchange walk* by looking ±600 m for another metro step (`:513-577`), and de-dupes events within 400 m (`:717-728`). `buildTransferBoundariesMeters` (`:300`) is a lighter metro-only variant used by `maptracking.dart`.

### Path B — Creation-time destination validation (network)

`MetroStopService.validateMetroRoute` (`metro_stop_service.dart:99`) is called once from `homescreen.dart:749` when a route is created. It fetches nearby transit stations from a live API through `ApiClient`, finds the closest stop to the destination and to the start, and rejects the route only if start and destination resolve to the **same `place_id`** (`:149`). It does *not* verify a metro path exists between them. Entirely separate from Path A's OSM data — a second, inconsistent source of truth.

## Key types & functions

- `Stop { id, name, location, line?, city? }` (`stop_matcher.dart:4`) — a candidate station; `line`/`city` optional so legacy call sites still compile.
- `MatchedStop { stop, snapped, distanceToPolylineMeters, metersAlongPolyline }` (`:25`) — a stop projected onto a route.

- `StopMatcher._projectPointOnSegment(a,b,p) → ({point,t})` (`:160`) — clamped projection **in raw lat/lng space** (see Gap E).
- `TransitLegStops { legStartMeters, legEndMeters, numStops, stopPositions, stopMeters, lineName?, isActualPositions, isMetro, stopNames, stopCountConfidence }` (`transfer_utils.dart:12`) — one metro/walk leg. `legId` getter builds a stable identity preferring stop-name topology (`:52-99`). `stopsPassed/stopsRemaining/copyWith/toJson/fromJson`. `fromJson` **heals** `numStops` to `stopPositions.length` when `isActualPositions` (`:145-147`).
- `TransferUtils.extractTransitLegStops(directions) → List<TransitLegStops>` (`:913`) — raw uniform legs.
- `TransferUtils.enhanceTransitLegStopsWithOsm(legs, directions, {stopsOverride}) → Future<List<TransitLegStops>>` (`:1281`) — the enhancement pipeline (Path A2). `stopsOverride` is a test-only seam.
- `TransferUtils.osmStopCountDiverges({apiNumStops, osmNumStops}) → bool` (`:1197`) — the G16 gate.
- `TransferUtils._canonLine(String?) → String` (`:1250`) / `_canonCity(String?) → String` (`:1269`) — stable identity tokens.
- `TransferUtils.buildRouteEvents / buildTransferBoundariesMeters / buildStepBoundariesAndStops` — event + boundary builders.
- `estimateStopPositions(polyline, numStops)` (`polyline_decoder.dart:109`) — uniform `j/(n+1)` placement (the fallback geometry).
- `MetroStopService.getNearbyTransitStops / validateDestination / validateMetroRoute` (`metro_stop_service.dart`) — network validator (Path B).
- `validate_metro_data.py:main()` — 8 checks over `metro_dataset.json`; hard errors gate CI, hop/dup anomalies are report-only.

## Design decisions (the WHY)

1. **Count stops instead of measuring distance-to-stop.** *Decided:* the metro alarm is driven by "N stops away," positioned in meters along the route. *Why:* underground GPS is dead, so absolute position is untrustworthy; but the train's progress along a known polyline (from dead-reckoning/EKF + the fixed route geometry) is knowable, and stops are fixed points on it. Counting is robust to GPS loss. *Trade-off:* it depends on an accurate station database and on Google's `num_stops`; a wrong count fires at the wrong stop. *Flaw:* there is no independent on-train sensor of "we just stopped at a platform" — the count is pure geometry against a static dataset.

2. **Ship the station database as hand-generated Dart (`allIndiaStops` + `kMetroLineSequences`), not the JSON assets.** *Decided:* bake the data into compiled Dart constants. *Why:* zero I/O, zero parse cost, guaranteed available offline the instant the app starts — exactly the underground scenario. No `rootBundle` race, no asset-missing failure mode. *Trade-off:* the data is frozen at build time and can only change with an app release. *Flaw:* the audited JSON (`metro_dataset.json`) and the shipped Dart are **two separate generated artifacts with no cross-check** (Gap B) — CI audits the JSON, but users run the Dart.

3. **Prefer polyline-domain meters over Google's `distance.value`.** *Why:* the live progress signal is a snap onto the stitched active polyline; boundaries must be in the same meter domain or "N stops before" fires at the wrong offset. *Trade-off:* extra polyline decoding; needs a gap-stitching fudge (`>5 m`) and a `legScale` reconciliation. *Flaw:* when step polylines are placeholders it silently falls back to API distances, mixing domains for that leg.

4. **LINE-FIRST ordered sequences for confident lines.** *Decided:* if a line has a trustworthy hand-ordered sequence, match *that* against the polyline instead of nearest-any-station. *Why:* radius matching against a nationwide pool can grab parallel/crossing-line stations; a pre-ordered own-line sequence gives exact count and order. *Trade-off:* requires maintaining `kMetroLineSequences`. *Flaw:* only 37 of 46 lines are confident; the 9 flagged lines (including **Delhi Blue**, one of India's busiest) have *no* runtime sequence and fall to the weaker line-filter path (Gap D).

5. **Exclude the 9 NN-reconstructed "flagged" lines from runtime sequences.** *Decided:* `build_line_sequences.py` emits confident lines only; flagged ones are dropped from `kMetroLineSequences`. *Why:* the ordering was reconstructed by nearest-neighbour chaining from a terminus, which jumps across the network on branches/loops — e.g. `delhi/blue` in `line_sequences.json` has `maxHopM: 21469` (a 21 km jump Akshardham→Dwarka Sector 9) and `confident: false`. A wrong *order* would mis-time every "N before." *Trade-off:* those lines lose the gold path and rely on line-filter + divergence fallback. *Flaw:* flagging is a *mitigation, not a fix*; the underlying ordering problem (branches/loops) is unsolved.

6. **Canonicalize line labels; anchor on color tokens; never merge line families.** *Decided:* reduce dirty OSM labels (`&#x25D9;  Blue Line`) and clean Google labels (`Blue`) to the same key, preferring a color word. Keep magenta≠pink, violet≠purple as distinct tokens (`transfer_utils.dart:1211-1231`). *Why:* Indian metros are colloquially "the Blue Line"; color is the most stable anchor, and Delhi genuinely runs *both* Magenta and Pink, Violet and Purple. *Trade-off:* numbered lines with no color collapse to a numeric join (`"Line 7"→"7"`), which is weaker. *Flaw:* labels that reduce to empty (e.g. Gurugram's `&#x25D9;  Rapid Line` → strip entity, strip `rapid`+`line` → `""`) yield an empty `legLineKey`, forcing the line filter to return nothing and the leg to fall back to uniform estimation every time (Gap C).

7. **Infer the leg's city by majority vote of matched stops.** *Why:* Directions legs carry no city; the stops physically on the polyline reveal it. *Trade-off:* needs ≥1 matched stop with a city label. *Flaw:* a mixed/border corridor, or a bad polyline that sweeps two cities' stations, could vote the wrong city → wrong `kMetroLineSequences` lookup (Gap F).

8. **The G16 divergence gate is asymmetric: distrust OSM, keep API-uniform + low confidence.** *Decided:* if OSM and Google disagree on count beyond `max(1, 20%)`, throw away OSM positions and keep the (safe) uniform leg flagged `confidence 0.5`. *Why:* firing late is product death; an OSM count that's *smaller* than reality would skip a stop and wake the rider too late. Uniform + "fire early" is the safe degradation. *Trade-off:* on divergence you lose real station geometry and revert to evenly-spaced guesses. *Flaw:* the gate compares only *count*, never whether stops are on-line; and a *within-tolerance* OSM count (off by up to ~20%) is adopted at full confidence 1.0 even if a stop or two is wrong, shifting where "N before" fires (Gap H).

9. **Multiple "never scoop the corridor" refusals.** *Decided:* when the own-line filter is empty or thin, refuse the nationwide corridor and keep the API-uniform leg (`:1461-1497`). *Why:* an on-route-by-construction uniform leg is always safer than injecting confirmed-off-line stations at wrong positions. *Trade-off:* accuracy sacrificed for correctness on messy lines. *Flaw:* none in direction of safety — but it means messy-label lines *silently* never get real positions.

10. **Endpoint (50 m) + next-leg (300 m) stop filtering.** *Why:* boarding/alighting stations are not "intermediate" stops (Google's `num_stops` excludes them) and would double-count; and on a metro→walk→metro interchange, the next line's boarding station geometrically leaks into this leg. *Trade-off:* fixed metric thresholds can clip a legitimately close real stop, or on a very short leg mis-classify one. *Flaw:* thresholds are hand-tuned constants, not adaptive to station spacing.

11. **`MetroStopService` uses a live network API, separate from the OSM inventory.** *Decided:* validate the destination against Google's live nearby-transit at creation time. *Why:* catches "you picked a destination nowhere near any metro." *Trade-off:* two sources of truth (Places `place_id` vs OSM ids) that can disagree; requires network. *Flaw:* it doesn't verify a metro *route* exists (only start≠dest by `place_id`); and if offline it returns "no stops found," which could wrongly block route creation. Contradicts the offline ethos, though it only runs at creation (presumably online).

12. **Color map keyed by clean human names, matched fuzzily.** *Decided:* `metroLineColors` uses names like `"Blue Line"`, and `direction_service._getLineColor` normalizes + substring-matches (`direction_service.dart:610-634`). *Why:* cheap, tolerant of dirty labels. *Trade-off:* cosmetic only. *Flaw:* substring fuzzy match can mis-color (e.g. `"Blue"` ⊂ `"Blue Branch Line"`); harmless to alarms but visually wrong.

## Invariants

- **`stopMeters` is monotonically non-decreasing** within a leg (relied on by `stopsPassed`'s early break; produced by arc-length ordering or ascending fractions).
- **`isActualPositions == true` ⇒ `numStops == stopPositions.length == stopMeters.length == stopNames.length`** (constructed together at `:1662-1675`; healed on deserialize at `:145-147`).
- **Never adopt an OSM count smaller/inconsistent enough to fire late** — enforced by the G16 gate; on any doubt, keep API-uniform + `confidence 0.5`.
- **Only own-line, same-city, active stations count as this leg's intermediate stops** (line filter + city guard + `_isActiveStop`).
- **Metro legs and extracted metro polylines are 1:1 by index** (both driven by the same `_isMetroTransitStep` predicate).
- **`metro_dataset.json` invariants** (enforced by `validate_metro_data.py`): each line ≥2 stops; `seq` contiguous `0..n-1` and unique; coords inside India bbox (lat 6–37.5, lng 68–98); no duplicate names within a line; `confident` flag consistent with the confident/flagged lists.

## Gaps & flaws vs the core promise

- **A — Frozen, un-updatable data (high).** Runtime stations are a compiled Dart snapshot (OSM 2025-12-25 + a yometro scrape). India opens metro stations and lines constantly; the moment a stop is added/renamed the count is wrong until an app release ships. There is no over-the-air data update path. Directly threatens "never at the wrong place" on new/changed lines.

- **B — Audited data ≠ shipped data (high).** `validate_metro_data.py` gates `metro_dataset.json`, but the app runs `allIndiaStops` + `kMetroLineSequences`, which are *separately generated* and *not* validated against the JSON in CI. The two can silently drift (station count, ordering, naming) and nothing catches it. The integrity guarantee the validator implies does not actually cover what users run.

- **C — Cities/lines with no confident sequence degrade to uniform guesses (high).** **Gurugram** (11 stations in `allIndiaStops`) is absent from both `metro_dataset.json` (19 cities) and `kMetroLineSequences` — its Rapid Metro is un-audited *and* has no ordered sequence. Worse, its OSM `line` label `&#x25D9;  Rapid Line` canonicalizes to the **empty string**, so the line filter returns nothing and every Gurugram metro leg falls back to evenly-spaced estimates. Same fate for any line whose label reduces to empty or to a garbage numeric join (Gurugram also has a malformed `"Line 1 Line, Line 2 Line"` label).

- **D — The 9 flagged lines lose the gold path (high).** Delhi Blue/Magenta/Orange/Pink, Bengaluru (unnamed)/Green, Ahmedabad Yellow, Mumbai Red, Nagpur Orange have no runtime ordered sequence. They rely on the line-filter + divergence gate; where OSM coverage is thin the count diverges and they revert to **uniform interpolation**. Delhi Blue is among the highest-ridership corridors in the country — precisely where accuracy matters most, and where it's weakest.

- **E — Snapping projection is in raw lat/lng space, not metric (medium).** `_projectPointOnSegment` weights Δlat and Δlng equally (`stop_matcher.dart:165-178`). At Indian latitudes 1° lng ≈ cos(lat)·111 km (~0.87–0.99× at 8–30°N), so the projection point and `metersAlong` are skewed east-west. Distances themselves use haversine (correct), but the snapped location/arc-length is geometrically biased. Small at 150–500 m scale, but it directly perturbs where each stop's meters land, and it's asymmetric by heading.

- **F — City inferred by majority vote (medium).** A border corridor or a malformed polyline that touches two cities' stations could vote the wrong `legCityKey`, mis-looking-up the ordered sequence. Rare, but a wrong-city sequence would badly misorder stops.

- **G — Uniform fallback is geometrically wrong even when the count is right (medium).** The `j/(n+1)` placement assumes evenly-spaced stations. Real metro stops are unevenly spaced (dense downtown, sparse suburbs), so on any fallback leg "3 stops before" fires at the wrong *physical* point even with the correct count. Given how many legs land on the fallback (Gaps C/D), this is common, not rare.

- **H — The divergence gate trusts count, not correctness (medium).** It compares only `|osm−api|` and adopts within-20% OSM counts at full confidence — a leg can be off by a stop or two yet be treated as ground truth. And its safe direction (fire early on divergence) depends on Google's `num_stops` being right; if Google under-reports, both OSM (rejected) and fallback inherit the error.

- **I — `MetroStopService` is an offline-hostile, redundant validator (low/medium).** Network-dependent, `place_id`-based, doesn't actually confirm a metro route, and can wrongly reject a valid destination when offline. It's a second source of truth inconsistent with the OSM inventory. Only mitigated by running at creation time.

- **J — Name-based dedupe can over- or under-merge (low).** `StopMatcher._normalizeStopName` strips `metro/station/railway/subway`; two distinct stations that normalize alike within 80 m merge (undercount → could fire late), while one station with two very different OSM names within 80 m won't merge (overcount → fires early, safe). The unsafe direction (undercount) exists but is narrow.

- **K — Fragile 1:1 leg↔polyline indexing (low).** `enhanceTransitLegStopsWithOsm` assumes the k-th metro leg maps to the k-th extracted metro polyline. Both use `_isMetroTransitStep`, so they normally align, but any divergence (a leg counted metro that a step predicate misses, or fragmented transit steps) would desync the index and snap stops onto the wrong leg's polyline.
