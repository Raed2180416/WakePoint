# GeoWake — Underground Data Hunt (verified 2026-07-24)

> Deep workflow: ~30 candidate datasets + methods checked by LIVE WebFetch to test/fix the km-scale underground StationAssociation drift. Honest verdict + the only viable $0 path.

## Verdict

No. As of 2026-07-24 there is no publicly downloadable dataset that is simultaneously (a) real underground/GPS-denied train motion, (b) IMU-rate sensors, (c) station-dwell-level position ground truth, and (d) commercially clean-licensed. Every hunt independently converged on this same gap across ~30 candidates checked by live WebFetch/WebSearch. The closest content match (ADVIO: real metro-station GPS-denied walks with barometer at 100Hz) is CC BY-NC (noncommercial, legally blocking for a shipped product). The closest license match with real train content (ETH-PBL, MIT) has almost no tunnel/GPS-denial and no metro station cadence. SHL (real subway class, barometer, "tunnel" context flag) is both paywalled ($40/mo, no free tier confirmed) and stated research-use-only by two independent secondary sources; its own site could not be reached to check the primary EULA. Nothing found can replace or supplement GeoWake's own 2 real Namma Metro rides for diagnosing the km-scale StationAssociation drift. The only honest path forward is: (1) self-collect more real rides with free logging apps (verified working today, $0), using OSM-derived (ODbL, commercial-OK) station/polyline ground truth, and (2) build a rigorously cross-validated synthetic generator calibrated on those real rides rather than on any external dataset, since none of the externally available data can calibrate metro-specific dwell dynamics without contaminating the validation.

## Fix hypotheses for the km-scale StationAssociation drift (each testable)

1. ZUPT/dwell-detection threshold mismatch: the accel/decel stop signature used to trigger StationAssociation was likely tuned on clean or synthetic motion and does not reliably fire against real handheld noise (phone shifting in a hand/pocket, rider weight shifts) -- test by running the ZUPT detector standalone against the real R1/R2 IMU CSVs' known dwell windows (arrival_t_s to next departure) and measuring miss rate and false-fire rate directly, independent of the full EKF pipeline.
2. Partial-reset bug: StationAssociation may nudge position/velocity toward the known station on a detected dwell but fail to reset the accumulated bias/covariance state, so integration error from before the snap continues propagating afterward almost unchanged -- test by checking whether the along-track error at Nallur (longer GPS-blind stretch, ~3km error) scales roughly with tunnel length/duration versus Majestic (~1.3km error); if error scales with blind-window length in a way consistent with continuous unreset drift rather than resetting to near-zero after each successful snap, this points at an incomplete state-reset on association rather than a detection failure.
3. Confidence-gate too conservative underground: the association's acceptance threshold (mentioned in prior session notes as a 'confidence-gated never-late cone') may rarely or never clear its gate on noisy real IMU, so dwells are detected but the snap is never actually applied, and the EKF silently free-runs the whole leg -- test by logging whether StationAssociation candidate events are generated but rejected by the confidence gate on the real R1/R2 traces, versus never generated at all; these are different bugs with different fixes.
4. Wrong-station or ambiguous-window snapping under pre-existing drift: if raw dead-reckoned position is already off by more than roughly half the inter-station spacing by the time a dwell is detected, the association logic may match to the wrong candidate station, or refuse to match at all (fail-closed) rather than force-snapping to the nearest plausible station -- test by checking whether inter-station spacing on the Nallur/Majestic legs is short enough for this ambiguity to plausibly occur given the observed drift magnitude before the first mid-tunnel dwell.
5. Missing along-track backward-GPS-error precondition (per existing memory note 'never-late oracle along-track blind spot'): roughly 18% of real GPS fixes violate the oracle's implicit forward-only-error precondition; if StationAssociation's snap logic (or its surrounding EKF update) implicitly assumes the same precondition when blending pre-tunnel GPS with the dead-reckoned estimate, a backward-biased real fix just before tunnel entry could seed the whole GPS-denied leg with an already-wrong starting position that no in-tunnel dwell detection could later correct -- test by checking whether the last GPS fix before each real GPS-blind window in R1/R2 shows anomalous along-track (not just cross-track) error relative to the true entry point.
6. No barometer/independent depth cross-check: without a fused depth signal, station identity or dwell-vs-slowdown ambiguity near curved/closely-spaced tunnel sections (e.g. Cubbon Park-area curvature) could go undetected by accel/gyro alone -- this is a structural gap (barometer not yet in the CSV/EKF pipeline at all) rather than a specific bug, but is testable by adding a baro column (real, once phyphox/Sensor Logger rides exist) and checking whether depth-derived station discrimination reduces the false-match/no-match rate versus accel/gyro alone.
7. Timestamp/clock misalignment between the manually-recorded arrival_t_s ground truth and the actual sensor stream t_s: if the ground-truth tap and the IMU/GPS clocks drift or were captured via different apps/clocks (a documented general risk in the tap-to-mark literature, e.g. the IPIN GetSensorData design specifically avoids this by logging ground truth in the same stream), the association logic could be evaluating the wrong time window entirely -- test by checking how the 2 existing real fixtures' ground truth was actually captured and whether it shares a clock with the IMU stream.

## Non-circular synthetic generator + validation protocol

Non-circular by construction (full protocol; the anti-circularity lever is that dynamics and noise are calibrated from sources structurally independent of the EKF's own process model, and validated on a real ride the generator was never fit to). NOISE MODEL: measured = true_value + turn_on_bias (const per-ride, drawn once) + bias_random_walk(t) (Gauss-Markov, driven by measured bias instability) + white_noise(t) ~ N(0, (noise_density*sqrt(fs/2))^2) at ~50-100Hz + scale_factor_error*true_value + fixed cross-axis misalignment. White-noise density comes from the Bosch/TDK datasheets (the one genuinely datasheet-sourced parameter, low risk). Bias instability is NOT taken from any external Allan-variance figure (datasheets don't publish it for consumer parts and it varies an order of magnitude by grade) -- instead run Allan-deviation analysis on the stationary dwell windows of GeoWake's own 2(+N) real rides (arrival_t_s to next departure, cross-checked against GPS speed~0), using standard open-source imu_utils/allan_variance_ros-style tooling. This keeps the noise floor calibrated to real handheld-in-pocket-or-hand human noise, which DATA_CONTRACT.md already identifies as the dominant term, not a sterile lab spec. DYNAMICS MODEL: jerk-limited (S-curve/trapezoidal-jerk) speed profile per station-to-station leg -- bounded-jerk accelerate to a_max/v_max, optional cruise, symmetric jerk-limited brake, then a randomized dwell. Fit (a_max, v_max, jerk, dwell-duration distribution) per leg directly from the real rides' true arrival_t_s sequence and known s_travel (in-domain, zero external dependency, strongest available source); cross-check the fitted values against published metro/rail jerk-limit literature (ASEE, Tyne & Wear, MDPI tram study, arXiv:1705.08012) as an out-of-domain sanity bound only once those papers are actually re-read (prior session's fetches of them returned unreadable binary/403s -- do not hard-code numbers from them without a first-hand table read). CRITICAL ANTI-CIRCULARITY RULE: the generator's dynamics math must be a structurally different implementation from whatever the EKF's internal process model assumes (check the EKF's exact [s,v,b]-style propagation form first, then deliberately do not reuse that code path or parameterization) -- if the EKF's internal model differs from true jerk-limited kinematics and StationAssociation still performs well on synthetic data, that demonstrates robustness to model mismatch, which is the real question. VALIDATION PROTOCOL (2-fold, the max rigor available with n=2 real rides): split R1 (Majestic) and R2 (Nallur), never calibrate and validate on the same ride. Fit generator params on R1 only. Generate a synthetic version of R2's real route (same polyline/stations/ground-truth s_travel as real R2 -- the controlled variable) with R1-fitted dynamics+noise and a fresh noise seed (not R2's actual recorded noise). Run the identical EKF+StationAssociation pipeline on real R2 and on R1-calibrated-synthetic-R2; compare along-track error-vs-time curves. ACCEPTANCE: synthetic must reproduce the qualitative failure already measured on real data (error accumulating rather than resetting at each station) within a loose tolerance (e.g. synthetic peak along-track error within 2x of real R2's peak at each GPS-denied station, similar StationAssociation fire/miss rate) -- not exact numeric match. If synthetic recovers cleanly where real data drifts 3km, the generator is under-noised or the dynamics are wrong and must not be trusted for further validation. Repeat with R1/R2 swapped. NEGATIVE CONTROL (do this before trusting anything else): run the EKF on a synthetic trace with true dynamics and ZERO injected noise -- this must produce ~0 along-track error; if it doesn't, the bug is in the EKF/generator integration math itself, not noise realism, and must be fixed first. Only after all of the above pass do synthetic traces of new stations/lines (where no real ride exists) become usable for broader scenario coverage, and even then must be labeled per the DATA_CONTRACT.md convention as generator-validated-on-2-real-rides-only. BAROMETER: not yet in the CSV schema; add a 4th file <name>_baro.csv (t_s,pressure_pa,temp_c) or a sparser appended column at 10-25Hz. Synthesize via station platform depth (from OSM elevation tags where available, else a flagged cut-and-cover ~10-15m vs deep-bore ~20-30m approximation) run through the barometric formula, plus datasheet-sourced MEMS baro noise (e.g. Bosch BMP3-series RMS ~0.03 hPa) and an explicit piston-effect transient event on tunnel entry/exit (a real, documented confound that must be modeled, not ignored, per the prior SOTA review).
