# GeoWake — Developer Dashboard & Testing Flow (deep-dive, 2026-07-24)

> Read-only code audit of the unified dashboard + the whole app-testing/simulation stack, against the founder's intended flow (USB phone + mock location + route sim + live EKF/ZUPT display + premium testing). Everything cited at file:line.

## The founder flow vs reality

Founder's described flow, step by step, with what the code actually does (all citations verified against current HEAD d0d76e5, one commit past the prior audit's 6f4710f snapshot -- that commit only touched wrong-direction alerts, unrelated to this surface):

1. "Connect the real app on a phone via USB debugging" -- WORKS structurally. `flutter run` on a USB-attached phone in debug/profile mode auto-enables PlaygroundBridgeConfig (lib/config/playground_bridge.dart:34-39, kDebugMode||kProfileMode, no dart-define needed) and SimulationClient connects to ws://127.0.0.1:8081 by default. BUT this requires `adb reverse tcp:8081 tcp:8081` (relay is localhost-only) and — unverified but highly plausible blocker — no android:usesCleartextTraffic or network_security_config exists anywhere in the Android project (grep-confirmed zero hits), and targetSdk 35 defaults to rejecting unencrypted ws:// since API 28. This was never runtime-verified in any prior audit (read-only constraint).

2. "Use a mock-location app to spoof GPS" -- WORKS. Geolocator.getPositionStream() is consumed completely unfiltered (lib/services/location_manager.dart:132-134, confirmed no isMocked check exists repo-wide), so an Android-designated mock-location app's spoofed fixes flow straight through the real GPS->EKF->alarm pipeline exactly like real GPS. Undocumented anywhere in the repo, but functionally sound. Caveat: incompatible with the dashboard's own "Start simulation" control, which flips _isSimulationMode and causes real/mocked GPS to be silently dropped (location_manager.dart:209-215).

3. "Set routes and start tracking" -- WORKS on the real app UI as normal; this is what calls LocationManager().start() and connects SimulationClient to the relay.

4. "See EVERY aspect of app logic live on a unified dashboard" -- PARTIAL, the weakest link. The relay (tools/relay_server.dart, confirmed present, plain WS broadcast, port 8081) and the bidirectional WebSocket wiring both work. trackingservice.dart:2453-2464 (confirmed unchanged at current HEAD) DOES broadcast rich EKF internals: ekf_s, ekf_sigma_s, ekf_v, ekf_mode, ekf_motion, ekf_alarm_s/sigma_s/v/mode. But unified_dashboard.dart's _handleAppState (confirmed at line 557, still only reads destination/active_key/snap_offset_m/progress_m into _metricDebug at line 614) drops every ekf_* key on the floor -- they only reach the browser as an unparsed raw-string dump in a scrolling event-log line, not a real EKF panel. Reachability/never-late cone state (sMaxMeters, fire status) is never even added to the broadcast payload in the first place. ZUPT fires for a REAL device are never broadcast at all (no zupt field in the WS protocol) -- ZUPT visibility only exists for the dashboard's own synthetic replay, and even there the map-marker code is dead (explicitly disabled with a "ghost marker spam" comment in ekf_test_controller.dart).

5. "Simulate EKF data for routes that don't exist (synthetic rides) to watch ZUPT logic + alarm fires" -- WORKS, but only in the browser's own isolated Dart isolate, disconnected from any real phone. EkfTestPanel + EkfTestController + ImuReplayEngineV2 (confirmed present, 4 curated routes + log replay) drive the actual production EkfOrchestrator/AlarmEvaluator/ReachabilityTracker classes in-process with real ZUPT/sigma/RMSE/alarm-lead metrics. This genuinely satisfies "simulate EKF for routes that don't exist" as a standalone capability. But the one bridge that would push this synthetic data onto a REAL connected phone -- the 'ekf_test_position' WS message (unified_dashboard.dart:783, confirmed still the only send-site, zero receivers) -- is dead: simulation_client.dart's message handler (confirmed via direct read: only handles 'ping', 'switch_route', 'simulation_update' via if-chains, not a switch statement as an earlier characterization implied, but functionally identical -- no case/branch for 'ekf_test_position' exists) silently drops it. Arbitrary (non-canned) polylines ARE supported by the engine (loadRouteFromPolyline, ekf_test_controller.dart:554-606) but only reachable from the offline CLI harness (lib/testing/harness_runner.dart, confirmed present), not from the live browser dashboard's route picker.

6. "Test the PREMIUM user experience (pass ladder ₹7/35/99/899, rewarded day-pass, guardian, anti-theft) without real purchases" -- MOSTLY MISSING as a live/interactive capability. Confirmed at current HEAD: lib/main.dart:112 still calls `MonetizationService.instance.init()` with zero arguments; `backendOverride` (monetization_service.dart:66-70) exists and is fully exercised in headless unit tests (test/monetization/pass_ladder_test.dart etc.) but is never wired to any real app entrypoint or dashboard control. The ONE thing that does work live on a real device today is the rewarded-ad flow, because AdService defaults to Google's official test ad unit IDs and configure() with real IDs is never called anywhere (ad_service.dart:28-37) -- so tapping "watch ad for a free day" loads a genuine test ad and fires grantRewardedDayPass for real. Guardian mode's mechanics (sms:/wa.me composer links) need no special infra but are gated behind the same missing Pro-entitlement bypass. Anti-theft is effectively untestable on any emulator (direct sensors_plus/battery_plus dependency, no injectable seam, no debug trigger) and there is no in-app debug menu anywhere for any of this (lib/debug/ only has journey-demo tools + a never-started dev HTTP server).

  BROKEN, do not rely on it: pushing the dashboard's synthetic EKF/ZUPT scenarios (from "EKF TEST" mode) onto this connected real phone -- the 'ekf_test_position' WS message it sends has no handler in simulation_client.dart and is silently dropped.

## Full capability map

### unified-dashboard
How to run: 1. Start relay: `dart tools/relay_server.dart` (listens ws://0.0.0.0:8081; must be running first).
2. Start dashboard: `flutter run -d chrome -t lib/main_unified_dashboard.dart --web-port 3000` (per doc comment at lib/main_unified_dashboard.dart:6).

If the device is an Android emulator (or to be safe on a physical device via adb), run `adb reverse tcp:8081 tcp:8081` so the device can reach the relay at 127.0.0.1:8081.
4. In the dashboard toolbar, toggle 'EKF TEST' to switch between (a) normal mode -- demo/app-pushed route + Start/Stop/Deviate/Speed/Warp controls that inject fake GPS into the connected phone via `simulation_update`, and (b) EKF Test mode -- a fully in-browser synthetic/logged-ride replay (no phone required) exercising the app's real EKF/ZUPT/alarm code in-process.
Note: `.agent/workflows/launch_simulation.md` at the repo root gives the same relay+adb-reverse steps but names a stale entrypoint (`lib/main_dashboard.dart`, which no longer exists in lib/ -- only main_unified_dashboard.dart, main_aggregate_dashboard.dart, main_playground.dart are present); use `lib/main_unified_dashboard.dart` instead.

### sim-dashboards-map
How to run: 1) Start the relay hub: `dart run tools/relay_server.dart` (binds ws://0.0.0.0:8081). 2) Start the dashboard: `flutter run -d chrome -t lib/main_unified_dashboard.dart --web-port 3000` (or `lib/main_playground.dart` for the lighter EKF-only variant, no Maps key needed). 3) Connect the real phone via USB and run the app in debug/profile mode so PlaygroundBridgeConfig.enabled is true (kDebugMode||kProfileMode by default; force with `--dart-define=PLAYGROUND_BRIDGE_ENABLED=true` on a release-style build). Since the relay is localhost-only, either `adb reverse tcp:8081 tcp:8081` for USB, or point the phone at the dashboard machine's LAN IP via `--dart-define=PLAYGROUND_RELAY_URL=ws://<lan-ip>:8081`. 4) Spoof GPS on the phone with a mock-location app, set a route in the real app UI, and arm tracking -- route_update/app_state/device_position now stream to the dashboard and render on its map with metrics (destination/key/offset/progress; EKF sigma/mode/motion are sent but NOT shown in the UI -- see gaps). 5) For in-dashboard synthetic EKF testing (no phone needed), use the embedded EKF Test Panel: pick one of 4 curated routes (or Log Replay) and hit Start Test to see live ZUPT/sigma/RMSE/alarm-lead metrics. 6) For a genuinely synthetic route that doesn't exist on any map, skip the dashboard UI and run the headless harness instead: `dart run lib/testing/harness_runner.dart scenario.json` with an arbitrary `[[lat,lng],...]` polyline in the spec. 7) There is no supported path to test the premium pass-ladder/guardian/anti-theft UX without a real or store-sandbox purchase -- FakePurchaseBackend exists but is unwired from any dashboard/debug entry point. 8) For semantic real-app UI automation, run the Maestro personas in test/maestro/*.yaml against a release build (the debug build was found to ANR on cold start).
