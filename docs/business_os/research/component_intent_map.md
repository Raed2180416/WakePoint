# GeoWake — End-to-End Component & Product-Intent Map

## Honest verdict

GeoWake keeps its headline promise only in the narrowest, most literal sense: the physics core that decides *when* to fire an alarm (Reachability's never-late cone, the EKF's tunnel-blind dead reckoning, the alarm-delivery layer's DND-bypass and dual live/OS-backstop firing) is genuinely rigorous, red-team-commented, and — on the specific path that's been tested — proven never late across a 391-ride synthetic corpus; this is not vaporware. But almost every promise layered on top of that core has a real, evidenced crack, and the cracks share a disturbing pattern: they are silent by construction. A bus rider gets wrong-mode routing with no signal anything's off. A rider who boards the wrong train gets a DND-swallowed notification instead of a wake-worthy alarm. A family member watching Guardian's live-share plausibly stares at "Waiting…" forever because an auth token was never wired in. Anti-theft detection lives in the one isolate least likely to survive the exact screen-off scenario it's marketed to survive. A phone rebooted mid-journey on a locked screen can leave the exact-alarm backstop disarmed until unlock, on precisely the aggressive-OEM device population (Xiaomi/Vivo/Oppo/Tecno/Infinix) this app explicitly targets, with none of that reboot path proven on real hardware anywhere in this repo. And underneath all of it, the revenue mechanism meant to sustain a free safety product for the long run is shipping with Google's test AdMob ID and unverified store SKUs — meaning the product may currently be earning nothing to keep itself alive. The honest verdict: GeoWake will very likely wake a metro rider who armed a correctly-recognized station on a phone that stays powered through the night — that specific, common case is well-earned. Everything adjacent to it — the bus half of "metro/bus," the safety-net-for-the-safety-net scenarios (reboot, wrong-train, theft, family reassurance), and the business model that funds it — ranges from partially working to structurally silent, and a team auditing only the in-app UI or the marketing copy would not know it.

## Top unserved user-intents (ranked)

- **[P0] Wrong-train/off-route warning is silent under DND — the exact protected rider gets nothing** (routing-deviation) — ActiveRouteManager correctly detects a half-asleep rider boarded the wrong train or drifted off-route, but escalates only to a `playSound:false, enableVibration:false` notification. DND (the modal state for a sleeping rider, and the exact condition the whole app is built to defeat) swallows it silently. The detector's output connects to nothing capable of actually waking the rider or preventing the failure it computed.
- **[P0] Reported-GPS-accuracy-only anchor gating leaves a proven residual late-fire hole in the 'never late' guarantee** (reachability) — Precondition (i) filters the reachability anchor's real-fix gate on reported GPS accuracy only, not EKF-internal phantom/multipath rejection. The codebase's own along-track-error test shows this can produce a genuine late fire when reported accuracy understates true along-track error (p99 ~782m vs median ~7m in the corpus) — a hole in the literal claim the product is named for.
- **[P0] Bus riders (half the stated 'metro/bus' market) have no working path to correct transit routing** (home-planning) — 'Metro Mode' is the sole lever for transit-vs-driving routing. Off, a bus rider silently gets car-driving ETA/routing with zero UI signal anything is wrong. On, MetroStopService rejects any destination not within 500m of one of 875 hardcoded metro-only stations. There is no UI path in this app today for a bus-only rider to get correct transit directions.
- **[P0] Guardian's 'family knows you're safe' push plausibly fails silently on every default build** (safety-features) — The arrived-safely backend call depends on GEOWAKE_SHARE_TOKEN, which no build script in the repo injects, and failures are swallowed by design (fail-open, correctly, for the core alarm). A worried family member watching the live-share link would just see 'Waiting…' forever with zero error surfaced to anyone — the exact scenario the feature exists to prevent.
- **[P0] Anti-theft snatch detection runs in the isolate least likely to survive the scenario it's sold for** (safety-features) — The one Pro safety feature whose entire premise is 'detect a snatch while I'm unconscious, screen off' runs in the foreground UI isolate, not the reliability-hardened background service the rest of the codebase deliberately built for exactly this scenario. Marketing copy claims it 'bypasses Doze, silent mode, and screen lock' — true only of the firing mechanism, not the detection mechanism that has to survive first.
- **[P0] Reboot / direct-boot / OEM-autostart chain is unproven on the exact device population this app targets** (native-plugin) — The backstop notification channel is only created when the UI Activity launches, not in the background isolate that posts to it after boot; no boot receiver is direct-boot-aware, so a mid-journey reboot on a locked phone (the modal overnight-bus-rider case) leaves the exact-alarm backstop unarmed until first unlock. - **[P1] The ETA/distance number the rider trusts is computed by 3-4 unreconciled writers that can disagree** (map-tracking-ui) — Two independent GPS streams and up to four overlapping listeners independently setState the same ETA/distance text with slightly different formulas — the number a groggy rider reads to decide whether to trust the app can visibly contradict itself within the same second.
- **[P1] Both revenue mechanisms are plausibly non-functional as shipped** (monetization-full) — The ad pipeline uses Google's public TEST AdMob application ID with no wiring anywhere to inject production ad-unit IDs, and the four IAP SKUs' existence/pricing in Play Console is unverified. It's plausible neither of the two funding mechanisms for this free-forever-core safety product is actually live.
- **[P2] RouteMemoryService ('learns your routes automatically') delivers zero benefit to free riders** (home-planning) — This is the app's stated design alternative to manual Home/Work — written on every single arm — but its only consumer (the home-screen widget) is Pro-gated. Free riders, who this no-manual-setup design exists to serve, see nothing from it.
- **[P2] The EKF's own diagnostic tooling is unwired, so the team has no field visibility into its riskiest safety net** (ekf-core) — TiltFilter's gravity-sensor fusion path is dead (silently downgraded to weaker accelerometer-LPF every ride), the on-device EkfLogger black-box recorder is never wired into the report-a-problem flow, and the ekfHealth cold-start telemetry flag is permanently false. The team cannot currently measure how often the cold-start-underground-boarding safety net actually fires in the field.

## Subsystem verdicts

- **entry-lifecycle**: The entry/lifecycle subsystem is unusually well-engineered for its stated intent: cold start is fast (services deferred off main(), splash does its own bounded-timeout init), and there are two genuinely load-bearing recovery mechanisms — SplashScreen's snapshot-restore tree and the background isolate's null-initialData recovery branch — that correctly reseed the never-late reachability anchor across process death rather than naively resetting it, which is exactly the kind of detail that matters for the sleeping-rider promise. The single biggest risk is that reboot/process-death recovery depends on two independently-wired, uncoordinated OS receivers (flutter_local_notifications' boot receiver for the backstop alarm, flutter_background_service's boot receiver for live tracking) plus OEM-gated autostart permissions that this code cannot force — and there is no on-device evidence in what I read that either half of that reboot path has actually been proven to fire on a real Xiaomi/Vivo/Oppo device, which is the exact device population this app targets. A secondary risk is unmanaged concurrency between the splash screen's own navigation, the crash-report dialog, and deep-link handling, all independent fire-and-forget async chains racing on the same root Navigator with no ordering contract.
- **home-planning**: The core one-tap arming spine (search → mode → validate → confirm → track) is coherent and fails closed at every gate, which is the right shape for a product whose entire value is 'trust it enough to fall asleep.' But two pieces of the flagship story are structurally unfinished: 'Metro Mode' is the sole lever for transit-vs-driving routing, so bus riders (half of the stated 'metro/bus' market) have no path to correct transit directions without also tripping metro-only stop validation that only recognizes 875 hardcoded metro stations; and the 'learns your routes automatically' design (RouteMemoryService) is written on every single arm but rendered nowhere a free rider can see, with its own cache-reuse optimization also dead code. Biggest risk: a bus-only rider silently gets driving-mode ETA/routing with zero UI signal anything is off, directly undermining the never-late guarantee for the use case the app claims to serve.
- **tracking-core**: The orchestrator's foreground/background plumbing (ACK-retry handshake, dual-path _onStart with genuine OS-kill recovery, wake-lock lifecycle, snapshot persistence, and a real GAP-driven fix for the cold-start-underground no-wake case) is more carefully engineered than a typical background-service wrapper — there's clear evidence of prior incident-driven hardening, not just happy-path code. The single biggest risk is that the mechanism specifically responsible for detecting 'the rider swiped the app away' (HeartbeatMonitor) is unconditionally disabled under isTestMode by construction, so the module whose entire job is background reliability is also the module with the least automated verification of its own core behavior — everything that matters here (ACK loss, heartbeat timeout, OS-kill recovery, wake-lock leaks) is real-device-only, unverifiable from this codebase's test suite alone.
- **location-sensors**: The subsystem's actual load-bearing path — LocationManager's real-vs-sim switching, speed/jitter smoothing, and SensorFusionManager's EKF wiring (GPS fix feed, no-gyro detection, GPS-silence-to-degraded-mode notification) — genuinely works and is reasonably careful (phantom-fix and off-route rejection, station-context plumbing). But the subsystem is riddled with dead observability scaffolding: GpsHealthMonitor (a whole class built to answer 'is GPS degraded/unavailable') is never instantiated anywhere; three separate UX hook callbacks (onGpsAccuracyRejected, onServiceStatusChanged, GpsHealthMonitor.stateStream) are fired but have zero consumers; the per-alarm accuracy gate (accuracyGateMeters) is documented as 'set by TrackingService' but never actually set, so it silently always uses the fixed 100m default; and the checked-in sensor_fusion_test.dart is not a test of the production class at all — it's a stale copy-pasted duplicate class with an empty main(), giving false confidence that GPS-dropout/EKF-feed logic is covered. The single biggest risk: LocationStreamHandler (813 lines, the actual glue between LocationManager, SensorFusionManager, and the alarm-during-blackout evaluation that is core to the 'never late' promise) has no unit tests at all, and the rider gets no proactive signal when Location is disabled mid-journey or when fixes are being silently rejected as coarse — the half-asleep Namma Metro rider just has to trust an EKF whose only real-time evidence of trouble is the notification's ETA looking stale.
- **ekf-core**: The EKF core (EkfPipeline, ZuptDetector, StationAssociation, GpsDegradationDetector) is genuinely well-engineered and, unusually for this codebase, honestly documents specific real production failures it was hardened against (518km spike, 242km blow-up, 300s-gap late fire, 138 off-route phantoms) -- this is not vaporware math, it is wired end-to-end into the real alarm decision (trackingservice.dart consumes ekf.s directly on metro/degraded legs) via SensorFusionManager, contradicting the orchestrator's own stale "not yet integrated into app" header comment. The single biggest risk is that everything proven about this subsystem is proven either mathematically (the pipeline's guard rails) or against a synthetic/replay harness (ImuReplayEngineV2's physics-modeled IMU, not recorded real-device noise/OS-batching behavior) -- genuine field-scale validation across diverse real Android hardware remains the open question. Three concrete, fixable gaps stand out: the documented gravity-sensor fusion path in TiltFilter is dead in production (never fed a real GravitySample, silently downgraded to the weaker accelerometer-LPF path every single ride), the on-device EkfLogger black-box recorder that would make real-rider failure reports debuggable is fully built but never wired in, and the ekfHealth cold-start telemetry flag is permanently false due to a nonexistent enum value -- meaning the team currently has no production visibility into how often the cold-start-underground-boarding safety net they built actually fires.
- **reachability**: The core physics math (free-run cone, piecewise multi-leg V_LINE, watchdog, statistical/physics fusion) is genuinely rigorous, deliberately proven with red-team-style comments, and is live in production across distance/time/stops modes with a 391-ride scale harness asserting zero late fires -- this part earns the "never-late" claim. However, the two components explicitly marketed as the real UX lever for reducing over-early wakes -- the stop-count dwell cap and the accel/brake/curve dynamic-levers profile -- are both fully inert in production (hardcoded dwellMinSeconds=0.0 and dynamicLeversEnabled=false), and the iOS backstop planner is dead code never wired to any app runtime, so a meaningful fraction of this subsystem's most interesting engineering delivers zero rider-facing benefit today. The single biggest correctness risk is precondition (i): production's real-fix gate for the reachability anchor filters only on reported GPS accuracy, not on any EKF-internal phantom/multipath rejection, and the codebase's own along-track-GPS-error test proves this can produce a genuine late fire when reported accuracy understates true along-track error (observed p99 ~782m vs median ~7m in the corpus) -- a residual, currently unmitigated hole in the guarantee's foundational assumption.
- **alarm-decision-fire**: The alarm decision + delivery subsystem is the most rigorously engineered part of GeoWake: the fire-decision math (reachability physics bound, per-mode never-late tests) and the presentation layer (insistent+no-clear flags, dual live+OS-backstop firing, layered audio/haptic fallbacks, no-snooze enforcement) are real, wired end-to-end, and one path has actual emulator evidence of firing (patrol_alarm_test.dart logcat). It genuinely serves the 'wake a sleeping rider through silent/DND/tunnel' intent for the common case. The single biggest risk is the total-process-death recovery path — the exact scenario the OS backstop exists for — where the cold-launched app's UI does not reconcile with 'a backstop alarm is currently ringing' (no _finalAlarmActive, no synchronous backstop cancellation tied to the live fire), and several audibility/DND/full-screen-intent claims remain proven only by comments marked DEVICE-VERIFY rather than by any on-device test evidence present in this repo.
- **native-plugin**: The native Android safety net is more real than a skeptical read of the docs would suggest: the DND-bypass fix, the flutter_local_notifications receiver declarations, and the full-screen-intent/DND preflight plumbing are all genuinely wired end-to-end and independently verifiable in bytecode and call graphs, not just comments. But the net has two concrete holes that directly undermine its 'survives OEM process death / reboot' promise: (1) the safety-critical backstop notification channel is only created when the UI Activity launches, not in the background isolate that actually posts to it, so a boot-only recovery path can post to a channel Android has never seen; (2) none of the boot receivers are direct-boot-aware, so a mid-journey reboot on a locked phone (the modal case for an overnight-bus rider) leaves the exact-alarm backstop un-armed until first unlock. Both are corroborated by the repo's own prior triage log as still-open, and both point at the same underlying pattern: the live-alarm path is well hardened, but the "OS-level, process-independent" backstop path still has UI-Activity-lifecycle and unlock-state dependencies it shouldn't have.
- **routing-deviation**: The routing/deviation/reroute subsystem is substantially real, not scaffolding: DirectionService's metro-preference and cost-guarding logic, TransferUtils' OSM-enhanced stop-counting with documented field-bug fixes ('MUMBAI FIX'), and RerouteConstraints' defensive multi-mode validation all show evidence of genuine iteration against real failures. The biggest risk is not any single stub but an integration seam: (1) a confirmed dead `hintIndex` parameter means the two deviation/reroute-decision snap calls (route_session_manager.dart:1140, 1178) run unwindowed, non-sticky nearest-point search instead of the connectivity-aware snap the rest of the system relies on, feeding possibly-noisy offsets into deviation/reroute decisions on any route with parallel or crossing track; and (2) the wrong-direction/wrong-train detector — built specifically for the 'half-asleep, boarded the wrong train' scenario — correctly detects the failure but only escalates to a silent (`playSound:false, enableVibration:false`) notification, meaning the one class of rider this whole app exists to protect (asleep, phone on DND) will not actually receive the warning it computed.
- **metro-data-eta**: The core historical failure mode this subsystem existed to fix — line-blind nearest-any-station snapping causing wrong-metro-station alarms — has genuinely been remediated: transfer_utils now carries line/city through the pipeline, filters matches to the leg's own line, prefers a hardcoded ordered per-line sequence when trusted, and has a 'never zero stops, never cross-line' safety net whose confidence signal is actually consumed downstream to fire alarms earlier rather than silently trusting bad data. The biggest remaining risk is that the hardcoded ordered sequences (kMetroLineSequences) for ~32 of ~37 'confident' lines were never independently verified beyond a pure-geometry nearest-neighbour heuristic with only a large-hop-distance sanity check — a topologically wrong-but-short-hop ordering (branch, loop, parallel corridor) would ship silently. Secondary gaps: MetroStopService's destination-validation path doesn't share the status/line-awareness the tracking-time path has (currently masked because no non-active stations exist in the data), the data-quality validation script that could catch regressions isn't wired into CI, and the ETA engine's metro-scheduled physics model and the transfer/interchange event logic are both far less test-covered than the basic straight-line ETA path.
- **map-tracking-ui**: The live-tracking screen delivers its two core promises — a visible, position-updating map with a reassuring "estimating from motion" banner during GPS blackouts, and an unambiguous, no-snooze "you've arrived" card — and both are implemented with genuine care for the half-asleep-rider use case (well-reasoned in-code comments, deliberate no-snooze design, freshness-gated GPS-out indicator). But the screen is riddled with duplicated, unreconciled state: two independent GPS streams both drive position updates, and up to four overlapping listeners independently setState the same ETA/distance/transfer-notice text with slightly different formulas, so the number a groggy rider trusts can visibly disagree with itself within the same second — a reliability smell directly adjacent to the product's core promise. The single biggest risk is the "black map" history: Google Maps platform-view rendering was found solid-black under software GL on emulators (blocking most on-device testing for months), reportedly worked around via release builds, but never confirmed fixed on real hardware — and the docs that tracked this are currently deleted from the working tree with no on-disk trace surviving outside git history.
- **monetization-full**: The monetization subsystem's SAFETY half of its mandate is genuinely solid: AdPolicy is a pure, exhaustively-tested denylist that hard-forbids ads on alarm/wake/lockScreen before it even consults Pro status, PremiumService's alwaysFreeCapabilities can never be gated, and post-arrival ad/upsell surfaces are provably sequenced strictly after alarm teardown by construction — this part earns the trust the product needs. The FUNDING half is where the real risk lives: the entire ad pipeline as shipped uses Google's public TEST AdMob application ID (android/app/src/main/AndroidManifest.xml:43) with zero wiring anywhere in the repo to inject real production ad-unit IDs via AdService.configure() — meaning production ads, if shipped today, would generate no real revenue. Combined with an unverified assumption that the four pass-ladder SKUs actually exist and are priced correctly in Play Console, and no server-side IAP receipt verification, it's plausible neither of the two revenue mechanisms is actually live yet, even though the gating/entitlement engineering around them is excellent. The biggest single fix-before-launch item is wiring real AdMob credentials (or explicitly deciding ads are IAP-only for v1); the biggest UX gap is that a paying pass user has no in-app way to see when their entitlement expires.
- **safety-features**: The Safety Pro subsystem is well-architected at the seams that matter most for trust: the fail-open invariant genuinely holds (verified via homescreen.dart's post-startTracking ordering, PostAlarmMulticast's microtask/try-catch isolation, and NotificationService.shouldSuppressAuxiliaryAlarm's pure suppression logic) — a bug in Guardian or anti-theft cannot delay or override the core wake alarm. But both headline features have a real gap between promise and delivery: Guardian's 'family knows you're safe' claim silently depends on a production auth token (GEOWAKE_SHARE_TOKEN) that no build script in this repo ever injects, so the default app likely 401s against its own live Railway backend for every live-share/arrived push, with all failures swallowed by design — the family member would just see the link stall on 'Waiting…' with zero error surfaced anywhere. Anti-theft's snatch-detection sensors run exclusively in the foreground UI isolate rather than the reliability-hardened background service isolate the rest of this codebase deliberately built for the exact 'screen off, app backgrounded, OEM kills the process' scenario the feature exists to survive — this is the single biggest architectural risk in the subsystem and has zero test coverage or real-device validation. The single biggest risk overall is that both gaps are invisible: fail-open error swallowing (correct for protecting the core alarm) also means these two failure modes produce no crash, no log a developer would notice, and no user-facing error — they'd only ever surface as silent trust failures ("my family never got told I arrived," "the alarm didn't go off when my phone was grabbed").
- **privacy-data-telemetry**: This subsystem is unusually well-engineered for its stated goal: consent defaults OFF and is enforced by a fail-safe parser, egress is genuinely triple-locked (compile flag + type-level ReleasedCell capability token + import-level absence of network code in the null sink), no coordinate survives past StationBinner.bin(), and a regression test already caught one real past incident (a hardcoded production egress URL). Telemetry is honestly local-only today and the user-facing report flow is genuinely user-initiated and PII-scrubbed. The biggest risk is not that this subsystem leaks data now — it doesn't — but that the on-device documentation undersells how much of "Phase B" already exists and is deployed (a live merge backend with public dashboard endpoints, jti-keyed k-anonymity that a re-authenticating device could game, and a candidate-upload path whose own client-side k-anon suppression would silently defeat the server's design even if fully turned on). A close second risk: the reliability telemetry this whole product depends on for measuring "did the OS kill us before the alarm fired" has a documented-but-never-wired flush() contract, meaning up to 31 events can be lost on exactly the kill it exists to detect.
- **permissions-reliability**: The subsystem is honest and well-engineered exactly where it's easiest to get right — the pure ReliabilityPreflightService decision core and its ReliabilityPreflightRunner wiring are the best-tested, most carefully fail-open code in the reliability layer, and they do genuinely refuse to arm a dead notification channel. But it leaks badly at the two places that decide whether a real rider ever reaches that point: the guided PermissionService grant flow silently aborts arming (zero feedback) on the exact refusals a half-asleep first-timer is most likely to make, while two other code paths (main.dart, notification_service.dart) fire overlapping OS permission requests blind before the user ever sees the careful rationale copy at all. The single biggest risk is structural, not a bug: the never-late OS backstop depends on SCHEDULE_EXACT_ALARM (not the non-revocable USE_EXACT_ALARM, dropped for Play-policy reasons) which is not auto-granted on stock Android 14 and is only advisory-severity by default, and the OEM-autostart deep-link table covers under half the manufacturers the preflight itself flags as aggressive — so for a meaningful slice of the India device mix (Tecno/Infinix/Itel explicitly, plus Sony/Asus/Lenovo/Nokia/etc.) the #1 documented missed-wake cause gets a soft warning with no working "Fix" behind it.
- **server-backend**: The Express proxy genuinely delivers its two core promises — the Google API key never reaches the client, and the wallet-drain guards (kill switch, family quotas, per-token quotas) are real, well-tested, and now CI-gated, not just documented. That is the honest good news: this is one of the more rigorously verified subsystems in the repo. The single biggest risk is a real, unexercised bug: the per-IP rate-limit keyGenerator trusts a client-spoofable X-Forwarded-For header with no `trust proxy` setting anywhere in the app, which plausibly lets an attacker bypass the auth-token-issuance rate limit — the layer the code's own comments call the primary defense against the public-bundleId problem — by rotating a fake header per request; the global per-family daily quota (not IP-keyed) is the real backstop that still caps total spend. A secondary, lower-urgency risk is the aggregate/ingest endpoint: it is live, reachable by anyone who can mint a token, has no rate/size guard at all (unlike every Maps route), and feeds an unbounded in-memory store — currently inert only because the shipped app's compile-time flag never calls it, not because the server defends itself.

The pattern across all 16: the **physics core of the "never late" promise is genuinely, rigorously real** (reachability math, EKF wiring, alarm delivery, server cost guards). Almost everything **adjacent** to that core — the second-order promises (bus routing, wrong-train rescue, family safety, phone theft, revenue, graceful degradation signaling, reboot survival) — has a concrete, evidenced gap between what's marketed/designed and what's shipped, and a disproportionate number of those gaps are **silent**: no crash, no log, no user-facing error, just a promise quietly not kept.

### [BROKEN] Per-IP rate limiting / slow-down (middleware/security.js) — server-backend
- what: express-rate-limit + express-slow-down wrap the general API, the auth-token-issuance endpoint (default 10 successful mints/hour), and the maps routes (1000/hour), all keyed by a custom keyGenerator that reads the request's own `x-forwarded-for` header directly (falling back to req.ip).
- intent: The auth-issuance limit in particular is meant to be the primary lever against the bundleId-is-public problem: 'capping how many [tokens] can be minted per hour matters more than IP-limiting the maps calls' (config.js:35-36 comment).
- evidence: geowake-server/src/middleware/security.js:13 and :30 — `keyGenerator: (req) => req.headers['x-forwarded-for']?.split(',')[0] || req.ip`. There is no `app.set('trust proxy', ...)` anywhere in the codebase (grepped src/*.js, none found), so Express never validates or strips this header — the code trusts the FIRST comma-separated value of a fully client-controlled HTTP header. Any caller can set a fresh, arbitrary `X-Forwarded-For: <random>` on every request and land in a brand-new rate-limit bucket each time, since most proxies (including Railway's edge, per config.js's own 'Railway env var' framing of the deployment) append their hop to the end of an existing XFF chain rather than replacing client-supplied values outright.
- intent gap: Because the global per-API-family daily quota (mapsGuard.js) is NOT keyed by IP or token, it still caps total dollar exposure even if this per-IP layer is fully bypassed — so the wallet is not fully unprotected, but the specific 'stop token-minting abuse per IP' control the comments describe as the important layer is not actually load-bearing as written.
- edge cases: This means the per-IP auth-token-issuance limit (the layer explicitly called out as the important one) is plausibly bypassable by spoofing a new X-Forwarded-For value per mint request, letting an attacker mint effectively unlimited tokens despite the documented 10/hour cap. The general and maps per-IP rate limiters have the same bypass.
- unvalidated: Whether Railway's actual edge proxy sanitizes/overwrites client-supplied X-Forwarded-For (which would neutralize this) was not verified — this analysis only establishes that the Express app itself does nothing to protect against a spoofed header, which is the code-level defect regardless of what the specific host happens to do today.

### [PARTIAL] Aggregate ingest + merge engine (mergeEngine.js, aggregateController.js, routes/aggregate.js) — server-backend
- what: POST /api/aggregate/ingest (auth required) accepts a client's locally-computed ReleaseCandidateMatrix and merges O-D/catchment cell counts into in-memory Maps keyed by cell string, tagged with the calling device's id; GET /summary, /flows, /catchment, /stats are public and only ever return cells that cross a k=100 distinct-device threshold, with Laplace DP noise (epsilon 0.44) added at release.
- intent: Let the founder eventually sell anonymized ridership demand data to transit operators/advertisers without ever exposing an individual rider's trip — the k-anon + DP math is the privacy promise buyers and Play Store's Data Safety form are told to rely on.
- evidence: geowake-server/src/utils/mergeEngine.js:1-254 (full engine, real k-anon suppression at lines 76-78 and DP noise at 228-236 — genuinely implemented, not stubbed math); routes/aggregate.js:20-27 (ingest gated by authenticateDevice only — no familyQuotaGuard/perTokenQuotaGuard/any rate limit specific to this route, unlike routes/maps.js:13-25 which guards every route); aggregateController.js:13-38 validates only `Array.isArray(payload.cells)` — no cap on cells.length, no per-cell field validation beyond what mergeEngine's `_parseCellKey` silently drops (mergeEngine.js:212-226). The app-side kill switch is real: `lib/services/data_asset/data_asset_config.dart:21` — `const bool kDataAssetEgressEnabled = false;` — a compile-time const, so the shipped app never calls this endpoint today (http_candidate_egress_sink.dart:57 no-ops when false).
- intent gap: Because ingest is reachable by anyone who can mint a token (the same public-bundleId gate as the maps routes) and is completely unguarded by the cost/rate layers that protect Maps spend, an attacker could POST arbitrary fabricated cells today — with enough distinct self-minted tokens (each counted as a 'device') to cross k=100 — and pollute the aggregate dataset the founder intends to eventually sell, or just grow server memory unboundedly. This is live and reachable in production regardless of the app's own compile-time kill switch, since that switch only stops GeoWake's own users from feeding it, not third parties hitting the API directly.
- edge cases: `_odCells` and `_catchmentCells` (mergeEngine.js:19-21) are plain Maps with no eviction, size cap, or persistence — they grow forever for the life of the process; nothing in the code prunes stale cells or bounds total memory, unlike cache.js's explicit maxKeys design a few files over.
- unvalidated: Never load-tested; k=100 threshold interacts with a device-id scheme that is the JWT `jti` (aggregateController.js:23, `req.device?.id`), which is minted fresh per token (authController.js:41) rather than a stable per-install id — so a real device that re-authenticates (24h expiry, or any 401 retry) presents as a 'new device' to the merge engine's contributor count each time, which was never validated against the k-anonymity assumption the release logic depends on.
