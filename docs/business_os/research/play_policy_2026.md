## Google Play Launch Requirements — GeoWake (checked 2026-07-24)

### 1. Target API level
- **New apps/updates must target API 36 (Android 16)** as of **August 31, 2026**; existing apps must target API 35 (Android 15) at minimum. An extension to Nov 1, 2026 can be requested via a Play Console form. [developer.android.com/google/play/requirements/target-sdk](https://developer.android.com/google/play/requirements/target-sdk)
- **GeoWake's current state**: `compileSdk 36` but `targetSdkVersion 35` (android/app/build.gradle:15,21). If you submit before Aug 31 2026, targetSdk 35 is compliant today, but bump to 36 before the deadline — don't leave it for the wire. Since compileSdk is already 36, bumping targetSdk should be low-risk; budget a real device/emulator regression pass on Android 16 behavior changes (notification trampolines, edge-to-edge enforcement, etc.) before flipping it.

### 2. ACCESS_BACKGROUND_LOCATION — declaration + disclosure
- Manifest already declares `ACCESS_BACKGROUND_LOCATION` (AndroidManifest.xml:6). This triggers a mandatory **Permissions Declaration Form** in Play Console (App content → Sensitive permissions) with three parts:
  1. What's the main purpose of the app.
  2. Describe **one** location-based feature that needs background access and why it can't work with foreground-only access — for GeoWake this is "wake the user with an alarm before their transit stop while the phone is asleep/screen off."
  3. A short video (≤30s recommended; YouTube preferred, Google Drive MP4 also accepted) that shows: the feature triggering from the background, the **prominent in-app disclosure dialog**, and the OS runtime permission prompt in sequence, matching real device behavior. [support.google.com/googleplay/answer/9799150](https://support.google.com/googleplay/android-developer/answer/9799150)
- **Prominent disclosure** (separate from the OS dialog) must appear in-app, immediately before the permission request (not buried in settings), state something like *"GeoWake collects location data to wake you up before your stop even when the app is closed or not in use"*, use plain "background"/"always"/"when closed" language, offer a real decline option, and match your written privacy policy exactly. Mismatches between the privacy policy and the declared behavior are one of the most common rejection triggers. [support.google.com/googleplay/answer/11150561](https://support.google.com/googleplay/android-developer/answer/11150561)
- **Common rejection reasons for transit/alarm-style apps**: insufficiently specific justification video, requesting background when foreground+FGS would suffice, location used for anything ads/analytics-adjacent, disclosure not shown at the right moment, and privacy policy not matching declared data use. Google's guidance explicitly says request the **minimum scope** (coarse over fine, foreground over background) — be ready to justify why coarse-only foreground service isn't enough for a "wake me before my stop" guarantee (answer: you need background wake capability for the alarm to fire while asleep/screen-locked).

### 3. FOREGROUND_SERVICE_LOCATION
- Already declared (AndroidManifest.xml:9), correctly paired with the `location` foreground service type. Requires its own Play Console foreground-service-type declaration (App content → Foreground service): describe the functionality, describe user impact if deferred, and provide a video link (can likely reuse/extend the same location-tracking demo video). [support.google.com/googleplay/answer/13392821](https://support.google.com/googleplay/android-developer/answer/13392821)
- Note: the app also declares `FOREGROUND_SERVICE_MEDIA_PLAYBACK` (AndroidManifest.xml:10) — that needs its own separate declaration and justification (alarm sound playback while screen-locked qualifies).

### 4. USE_EXACT_ALARM vs SCHEDULE_EXACT_ALARM
- **Policy**: `USE_EXACT_ALARM` (auto-granted, no runtime prompt) is restricted to apps whose **core, primary function** is "an alarm or timer app" or "a calendar app that shows event notifications." `SCHEDULE_EXACT_ALARM` (user-granted via Settings) is the fallback for everything else needing precise timing. [Play Console policy summary corroborated via support.google.com/googleplay/answer/9888170 and community threads]
- **GeoWake currently declares BOTH** (AndroidManifest.xml:19-20). This is a real risk: GeoWake's core function is transit tracking/navigation with an alarm as the payoff, not a "dedicated alarm clock" in the way Google's reviewers interpret the carve-out — a reviewer could plausibly reject the `USE_EXACT_ALARM` declaration as not qualifying. This matches the memory note ("drop USE_EXACT_ALARM") — **recommend dropping `USE_EXACT_ALARM` and keeping only `SCHEDULE_EXACT_ALARM`**, which just costs one extra user-facing Settings toggle ("Allow setting alarms and reminders") rather than a possible policy rejection/appeal cycle late in the launch process.

### 5. FULL_SCREEN_INTENT (Android 14+)
- Already declared (AndroidManifest.xml:13). Since Android 14, `USE_FULL_SCREEN_INTENT` is a **special access permission**, auto-granted at install **only** to apps whose core high-priority use case is alarms or incoming calls; Play can revoke the default grant for apps that don't fit that profile, and the user can also revoke it manually. GeoWake's wake-alarm use case should qualify, but expect Play's automated/manual review to specifically check this — build the in-app fallback path (`ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT` settings deep link + a heads-up-notification fallback if the FSI permission is revoked) so a mid-life revocation doesn't silently break the wake alarm. [support.google.com/googleplay/answer/13392821](https://support.google.com/googleplay/android-developer/answer/13392821), [developer.android.com/about/versions/14/behavior-changes-14](https://developer.android.com/about/versions/14/behavior-changes-14)

### 6. Data safety form
- Must be filled in App content → Data safety, and must **exactly match** what the app actually collects/shares and what the privacy policy states. Given `ACCESS_FINE_LOCATION`/background location usage, "Approximate location" and "Precise location" are both in-scope categories to declare, with purpose = "App functionality," collection = yes, sharing = per your actual pipeline (GeoWake's data pipeline is currently zero-egress/opt-in per memory — declare accordingly, and re-declare truthfully the moment egress goes live). Mismatches here are a top rejection/suspension cause in 2026 enforcement (255k+ apps blocked from excess access, 80k+ accounts banned in 2025 per Google's own reporting). [support.google.com/googleplay/answer/10787469](https://support.google.com/googleplay/android-developer/answer/10787469)
- Also declare: Guardian auto-share feature (contact/location sharing with a third party — a "shared with third parties" data-safety item), anti-theft feature if it captures device/location signals, and any ad SDK data collection for the free-tier ads.

### 7. New personal developer account: closed testing gate
- **Still fully in force in 2026.** Personal developer accounts created after Nov 13, 2023 must run a closed test with **≥12 opted-in testers, continuously enrolled for 14 consecutive days** (lowered from the original 20-tester requirement in Dec 2024), before Production/pre-registration access unlocks. Testers who opt out before day 14 don't count, and the 14 days must be unbroken. Verify whether your Play developer account predates Nov 13 2023 — if so, this gate doesn't apply; if it's a new/near-new account, budget it into the timeline explicitly. [support.google.com/googleplay/answer/14151465](https://support.google.com/googleplay/android-developer/answer/14151465)

### 8. Fees, review timelines
- **$25 one-time** Play Console registration fee (no recurring charge, unlimited apps per account). [multiple corroborating sources — see below]
- Separately, **from Sept 30, 2026**, Google is rolling out **Android Developer Verification** (identity check, ADPS-style) for apps distributed to *certified* Android devices, initially only enforced in Brazil, Indonesia, Singapore, Thailand, expanding globally in 2027. Not an India-specific blocker yet, but track it — global expansion could hit India in 2027 and require its own identity-verification step separate from the $25 Play Console fee. [developer.android.com/developer-verification](https://developer.android.com/developer-verification)
- **Review timeline**: first-time submissions commonly take **7-14 days** end-to-end (a few days of automated+manual review, sometimes 3-7 days if flagged for manual follow-up), **on top of** the mandatory 14-day closed testing window if your account is subject to it. Realistic total lead time from "closed test starts" to "live on Play" for a new personal account: **~3-4 weeks minimum**. Sensitive-permission apps (background location, exact alarms, FSI) commonly see longer/manual review passes — pad further.

### 9. Upcoming policy change to watch (not a launch blocker, but track)
- **October 28, 2026**: new Contacts Permissions policy (mandates Android Contact Picker over broad `READ_CONTACTS` where sufficient) and updated Location Permissions policy (recommends a "location button" as minimum-scope precise-location UX) become enforced — but **only for apps targeting API 37 (Android 17)+**. Since GeoWake will be targeting API 36 at launch, this doesn't block the Play 2026 launch, but note it for the next targetSdk bump cycle, and if Guardian/contact-sharing features read contacts, plan the Contact Picker migration ahead of that deadline. [support.google.com/googleplay/answer/16926792](https://support.google.com/googleplay/android-developer/answer/16926792)

### 10. India: DPDP Act 2023 obligations
- DPDP Rules were notified **Nov 13, 2025**, starting an 18-month phased rollout:
  - Phase I (now, from Nov 13 2025): Data Protection Board established.
  - Phase II (from **Nov 13, 2026**): Consent Manager registration framework goes live.
  - Phase III (from **May 13, 2027**): full operational obligations — notice, consent mechanics, breach notification, data-principal rights, children's-data protections, cross-border transfer rules — become enforceable.
- **Practical read for GeoWake's 2026 launch**: DPDP substantive enforcement (May 2027) is after your launch window, so it's not a hard Play-listing blocker today, but Play's own Data Safety form + prominent-disclosure requirements already force you to have consent/notice UX in place — build it DPDP-shaped now (specific, informed, unconditional, unbundled consent — not one "accept all" toggle covering location + Guardian sharing + ads) so you're not retrofitting before May 2027. Penalties for non-compliance once enforced can reach ₹250 crore (~USD 30M) for serious violations — worth flagging to make sure the opt-in mobility data pipeline's consent flow is unbundled from core app permission grants. [DPDP Rules 2025 coverage — Hogan Lovells, Wikipedia summary — see sources]
